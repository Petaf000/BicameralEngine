# ADR-0031 Luau のパッケージ: 1 フォルダ = 1 パッケージ、依存 → 名前の順に読み、表は「分類 → 鍵」で合わせる(合わせ方は設定で切り替え)

- Status: Accepted(形と実装の細部)/ **表の合わせ方の既定は仮(ユーザー未確認。QUESTIONS Q8 で案 C を仮に選んだ)**
- 日付: 2026-10-09
- 決めた人: Claude(実装の細部。CLAUDE.md §5)。上書きを許すかどうか(Q8・D-320)はユーザーが決める。T-0138

## 背景
- 13 §2: 1 つのパッケージ = 1 つのフォルダ(ゲーム本体もパッケージの 1 つ)。読み込む順番と、表の合わせ方(上書き・追加)を決める。
- D-320: Mod 前提・データ形式に版を付ける・反応表の改造と「法則を発見する」遊びの兼ね合いはユーザーが決める(Q8 が未回答)。
- 原則 3: 同じパッケージ群なら同じ表(13「テスト」)。フォルダを並べた順・入れた順・Luau の pairs の順番に依らないこと。
- 殻(ADR-0030)は require を開いていない。パッケージの中だけを読む require が要る。

## 決定
1. **パッケージの形**: フォルダの中の `*.luau`(下のフォルダも)。`package.luau` が `{ format = 1, depends = {...}, entry = "init" }` を返す
   (depends・entry は省ける。知らない欄は誤り)。entry のファイルが「分類 → 鍵 → 値」の表を返す(例 `{ reactions = { burn = {...} } }`)。
   パッケージ・分類・require のパスの区切りの名前は英小文字・数字・`_`・`-`(Windows と他の OS で大文字小文字の扱いが違っても同じになるように)。
2. **require はパッケージの中だけ**: `require("sub/util")` → 同じパッケージの `sub/util.luau`。`..`・絶対パス・拡張子つき・ほかのパッケージは届かない。
   殻の `RunOptions::modules` がある Run だけ、そのスレッドのグローバルに require を置く(殻のグローバルには無いまま。マニフェストでも見えない)。
   モジュールは自分用の環境(書き込みはそこ、読むときは Run のグローバルへ抜ける)で **1 つの Run の中で 1 回だけ**走り、戻り値をキャッシュする。
   循環は誤り(経路をメッセージに出す)。失敗したモジュールは「読み込み中」に残らない(pcall で捕まえて呼び直すと同じ誤りになる)。
3. **読む順番**: 依存の後。依存で決まらない所は**パッケージの名前(バイト順)**。`basePackage`(ゲーム本体)を決めると、ほかの全部がそれに依存する。
   依存が無い・読まなかった・循環 → そのパッケージ(と依存するもの)を読まない。理由を `rejected` に残し、ほかは続ける。
   プレイヤーが Mod の順番を手で並べる仕組みは入れない(同じ Mod の組なら誰の PC でも同じ順番・同じ表になる)。
4. **表の合わせ方**(`MergeMode`): 鍵は「分類 + 鍵」、値は丸ごと置き換え(中の欄ごとには合わせない)。新しい鍵は必ず足せる。既にある鍵を書くと:
   - `AddOnly`: そのパッケージを丸ごと読まない(全部か無しか。依存するものも)。
   - `OverrideMarked`: 上書きし、`overrides`(分類・鍵・前のパッケージ・書いたパッケージ)に記録し、**「改造された世界」の印 `modifiedWorld`** を付ける。
   - `Override`: 上書きし記録するが、印は付けない。
   仮の運用(Q8 の案 C): 既定は `AddOnly`、プレイヤーが上書きを許す設定にすると `OverrideMarked`。印の扱い(実績・共有)は決めていない(取り出せるだけ)。
   Q8 が A なら既定を `Override` に、B なら `OverrideMarked` を設定から外すだけで済む。
5. **値の形**: Luau の値は `ScriptValue`(nil・真偽・数・文字列・表)に直して持つ。表の鍵は数(小さい順)→ 文字列(バイト順)に並べ直す
   (pairs の順番に依らない)。関数・userdata・vector・スレッド・NaN・自分を含む表・64 段より深い表は誤り(ベイクに渡せない・決定的でない)。
6. **表の版**: `TableBytes`(分類・鍵・値の正準なバイト列。誰が書いたかは入れない)の FNV-1a 64 を `TableVersion` とする。
   同じ中身の表なら、パッケージの組が違っても同じ版(同じ法則の世界)。再生ファイル・発見の共有には、版と読んだパッケージの一覧の両方を残す(15 §4)。

## 検討した代案と、採らなかった理由
- 読む順番をプレイヤーが並べる(Mod の一覧の順): 同じ Mod の組でも人によって表が変わり、発見の共有(D-110)で再現できない組が増える。
  依存で順番を指定できるので、作る側が「この Mod の後」を書けばよい。要るなら後で `after`(弱い依存)を足す。
- 上書きを欄ごとに合わせる(深い合わせ): 「燃える速さだけ変える」Mod が書きやすいが、どの欄が誰のものかが分かりにくく、上書きの記録も細かくなる。
  先に丸ごとで始め、要れば足す(取り消しやすい方)。
- 表の版にパッケージの名前を入れる: 中身が同じでも版が変わり、同じ法則の世界どうしで発見が共有できなくなる。名前は別の欄で残す。
- require で他のパッケージのモジュールも読めるようにする: 依存の順番とは別の結びつきが増え、読み込みの順番に依る挙動が入りやすい。
  パッケージどうしは合わせた表でつながる。要るなら後で「依存先の公開モジュール」だけを足す。

## 影響(何がしやすく/しにくくなるか)
- しやすい: Mod を入れた順番・フォルダの並びに依らず、同じ組なら同じ表と同じ版になる。誤った Mod があっても、ほかは読める(理由が出る)。
  上書きを許すかどうかは設定 1 つで切り替わり、上書きの中身(誰の何を)を取り出せる。
- しにくい: 上書きは値を丸ごと置き換えるので、元の値の一部だけを変えたい Mod は全部を書き直す。ほかのパッケージの表を読んで足す道具はまだ無い。
- 残り: 削除(Mod が本体の反応を消す)の扱いは無い(上書きの一種として Q8 と一緒に決める)。ゲーム本体を複数のパッケージに分けたとき、
  本体どうしの上書きも「改造」に数えるかは未定(今は数える)。
