# ADR-0011 シミュは 1 フレームの予算ぶんずつ投げる(目標 fps は設定、既定 60)

- Status: Accepted
- 日付: 2026-09-30
- 決めた人: ユーザー(Claude が測定と代案を出した。T-0085)

## 背景
T-0004 で、1 刻みの Dispatch が長いと、描画はシミュを待っていないのに fps がシミュのバッチの速さまで落ちた(R-LOOP-2)。
T-0085 で測ると、この GPU(RTX 3070 Ti・HAGS 有効)では**描画は compute のキューに先に積まれた仕事が終わるまで始まらない**。
1 本のリストの中で Dispatch を細かくしても、別々の投入に分けても、vsync や描画のキューの優先度を変えても、fps は変わらなかった。
CPU が 1 フレームに予算ぶんだけ投げると描画は戻る(docs/perf.md 2026-09-30、06 §4.2)。
残る選択は、重いときに 1 フレームの GPU 時間を描画とシミュでどう配るか。

## 決定
- CPU は毎フレーム、**そのフレームの予算ぶんのシミュの単位だけ**を compute に投げ、その後ろに描画を投げる。描画より前に compute に積まれている仕事を予算以下に保つ。
  1 刻みは何フレームにまたがってよい(描画は完成済みの最新の抽出を読む)。
- 単位は 1 刻みの段を活性ブロックの一覧などで分けたもの(目安 1〜3 ms)。単位の数は読み戻した GPU 時間から決める(待たない)。
- **予算 = 目標のフレーム時間 − 描画の GPU 時間 − 余裕。目標 fps は設定で、既定 60。**
  重いときは描画を目標 fps まで落とし、残りを全部シミュに回す。軽いときは画面の上限で回る。目標 fps は 30(D-201 の下限)より下げない。
- 世界の結果は投げ方に依存しない(06 §1。T-0012 のテストで確かめる)。

## 検討した代案と、採らなかった理由
- 画面のリフレッシュレート優先(描画は常に vsync の上限、シミュは残りだけ): 165Hz だと 1 フレーム約 5 ms しか回せず、重いと世界の速さが最大の 7 割程度に落ちる。
- 30fps まで落としてシミュ最大: 世界は最速だが、カメラと UI の手触りを常に最低ラインにする。設定で 30 にはできるので既定にはしない。
- 1 刻みを分けずに投げる(T-0004 の形): 重いと描画がシミュのバッチの速さ(28fps 以下)まで落ちる。
- GPU 側で、compute に「まだ投げていない描画のフェンス」を待たせて歩調を取る: 試した実装に誤り(同じリストの二重投入)があり固まった。正しい形では未確認なので採らない。

## 影響(何がしやすく/しにくくなるか)
- T-0012 の刻みのループは、刻みを単位に分けてフレームにまたがって進める形になる。T-0004 の「バッチを 2 つまで重ねる」は置き換える。
- Work Graphs(T-0005 以降): 1 回の DispatchGraph が予算を大きく超えないよう、1 回で扱うレコードの数に上限を持たせ、続きを次の単位へ回す形が要る。
- フレームの切れ目で GPU が空く分だけ、重いときの世界の速さは最大より少し落ちる(目標 60fps で 36 ms/刻みなら 97% 前後。06 §4.2)。
- AMD など他の GPU で描画と compute が本当に並んで走るなら、予算はもっと緩められる(D-207。未確認)。
