# ADR-0019 細かいレベルの熱の陰解法は、近似解から面の流れを出し、誤差の見込みで反復を止め、外れたセルは陽解法に戻す

- Status: Accepted(CPU の試作の形。GPU〔T-0117〕と木への組み込み〔T-0119〕もこの形で進める)
- 日付: 2026-10-06
- 決めた人: Claude(実装の細部。CLAUDE.md §5。方式②を研究として進めることはユーザーが決めた〔D-432〕。T-0110)

## 背景
- 方式①(レベルごとの小刻み。ADR-0017 追記)は基準 + 3 段まで。それより細かい所は 1 段ごとに約 1/4 遅い(T-0108)。D-432 で方式②(陰解法)を研究に。
- 陰解法の連立方程式を GPU で決定的に解くには、回数が決まった(または決定的に止まる)整数の反復しかない。反復は収束し切らない。
- 保存則(D-206)はビット単位で守る。近似が効いてよいのは「どれだけ正しい速さか」だけ(D-428: 測れる嘘は入れない)。

## 決定
1. **1 刻み = 後退 Euler**: C_i (T_i − T0_i) = Σ g_f (T_j − T_i)。近似解 T* を木の多重格子(覆われた親へ縮約。親の係数 = 子の合計 ÷ 2)の
   V(2,2) サイクルで求める。重み(係数 ÷ 対角、Q48)は段を作る時に 1 回割る。係数は 128bit(R8)、温度は mK × 2^16。
2. **エネルギーは面の流れで動かす**: F = g (T*_細かい側 − T*_粗い側) を ADR-0017 の形(面ごとに 1 つの値を両側で逆向き・違うレベルは細かい側が計算し
   粗い側は整数部 + 端数)で足す。T* が収束していなくても保存はビット単位。
3. **反復は「新しい温度の誤差の見込み」で止める**: 各 V サイクルの後に、全部のセルで |残差| × D/C(D = C + Σg)≤ 1 mK なら止める(上限 16 回)。
   流れで足すので T* の誤差は D/C ≈ 4^Δk 倍で新しい温度に出る。判定は整数なので、同じ入力なら CPU でも GPU でも同じ回数。
4. **安全網**: 足した後のエネルギーが「刻みの初めの全部のセルの温度の最小〜最大(+ 1 mK)」の外に出るセルは、全部の面を陽解法の流れ
   (係数を熱容量の上限で頭打ち。1 面 ≤ C/8 なので凸結合 → 範囲の中)に戻す。戻すと隣が外に出ることがあるので、外に出るセルが無くなるまで
   「全部のセルを見る → 全部の面を直す」を繰り返す(戻したセルは二度と出ない → 必ず終わる。順に依存しない)。何セル戻したかを数える。

## 検討した代案と、採らなかった理由
- **回数を固定(V 2 回)**: なめらかな場では Δk 8 まで正確(0.991)で費用もレベル数に比例するが、鋭い熱い点(差 6 の面)では 10 万 K 行き過ぎた。
  安全網で抑えると、そこは陽解法の遅さに戻る(T-0110 の計測)。
- **赤黒の掃き出しだけ**: Δk ≥ 4 で熱が速すぎる(実効 1.1〜1.4 倍)。収束が遅い。
- **RKL2(super-time-stepping)**: なめらかな場は正確だが段の数が 2^Δk に比例(Δk 6 で 88)。鋭い所を減らす力が弱く(短い山が 1 刻みで半分残る)、
  熱い点で 6.4 K 行き過ぎた。
- **安全網の範囲を近所(自分と隣)にする**: 収束した解でも 4^Δk 倍の 0.1 mK 程度の揺れで外に出て安全網が連鎖し、全部が陽解法に戻った。
- **新しい温度を T* そのものにする**(AMReX のふつうの形): 保存が反復の許容差までしか守れない(ビット単位でない)。
- **多重格子の直しを 1.5〜2 倍にする**(区分的に一定の補間でよくある): この系では発散した。0.75 倍・Galerkin は改善したが届かない(T-0118 で続ける)。

## 影響(何がしやすく/しにくくなるか)
- 基準より細かい所(試験で Δk 8 まで確かめた。現実の空気なら基準 8 + 8 = レベル 16 ≒ 7.5 µm)も本当の速さ(±1%)で熱が伝わり、保存はビット単位・新しい最高/最低の温度は出ない。
- **費用が一定でない**: なめらかな場では 1 刻みに V 1〜6 回、鋭い熱ができた刻みは最大 16 回。GPU では「止めるか」の判定を毎回挟む(T-0117 で費用を測る)。
  予算(ADR-0011)を超える時の扱いは、計測の後にユーザーに遊びへの影響の形で聞く(T-0110 の「判断待ち」の見込み)。
- 方式①と混ぜられる(違うレベルの面はどちらも ADR-0017 の形)。どこから②にするかは T-0117 で測って決める。

## 追記(2026-10-06、T-0117: GPU の形と方式①との組み合わせ。決めた人: Claude〔実装の細部〕)
- **GPU の形**: 式は shaders/common/implicit_conduction.hlsli(CPU と共通)。段は Compute(shaders/sim/implicit_conduct.hlsl)で 1 スレッド = 1 節、
  V サイクルの段ごとに Dispatch(CPU の VCycle の再帰と同じ順)。値は 2 本を赤黒の色で入れ替え、縮約は親ごとに子の一覧を、流れを足すのはセルごとに
  自分の面の一覧(面の番号の昇順)を回す(atomic の足し算を使わず CPU の順と同じ)。HW・WARP で毎刻みビット一致(回数・安全網も一致)。
- **止める判定**: 判定は全部のセルの OR を状態の語に → 1 スレッドの段が「止めた」を書く。記録は上限の回数だけ積み、以降の回は述語(SetPredication)で
  Dispatch ごと飛ばす(段の中でも状態の語を見て空で抜ける)。安全網の繰り返しも同じ(記録は上限 16 回。止まらなければ GpuImplicitCost::limitFinished が false)。
  代案: 間接の起動・Work Graphs は、飛ばしてもバリアが残る点は同じで、空の回の費用は Dispatch 1 回あたり約 0.9 µs(述語)→ 減らすのは T-0120。
- **方式①との組み合わせ: 案 a(基準より細かい所は全部②)を仮に採る**。鎖の場面の見込みで 初めの刻み ≈ 2.2 ms・落ち着いた後 ≈ 1.9 ms/刻み
  (案 b〔基準 + 2 までは①〕は ≈ 5.1 / 3.0 ms、①だけ Δkmax 3 は 8.4 ms。T-0117 の表)。どちらも本当の速さ(①は 0.996・②は 0.991)なので遊びは同じで、
  安い方と、方法が 1 つで済む方を採った。見積もりは一部のセルを取り出したもの(外は断熱)なので、T-0119 で本物の木につないで測り直し、逆転したら直す。
- **上限の回数**: 今は 16 のまま(既定)。鋭い熱で上限に当たる時に (A) 解き切る / (B) 打ち切る はユーザーの判断待ち(T-0117 の「判断待ち」)。
  計測では打ち切ると次の刻みも届かず、遅い熱が続いた(熱い点で上限 8 なら 12 刻みの全部で 200〜1000 セルが陽解法に戻った)。

## 追記(2026-10-06、T-0120: GPU の固定費を減らす形。決めた人: Claude〔実装の細部〕)
- **長い行はグループで足す**: 隣を足す段(掃き出し・縮約・止める判定)は節の並び(u9)を回し、隣が 16 個を超える節は 1 グループ(64 スレッド)= 1 節で
  隣をスレッドで分けて足す(groupshared の木で和)。整数の和なので足す順によらず CPU と同じ値(04 R1)。掃き出しは色ごとに並びを分け、縮約は子の隣の最大で分ける。
- **小さい段から下は 1 Dispatch(ImTail)**: 節が 1024 以下・隣が 32 以下の段から最も粗い段までの V サイクルを 1 グループ(1024 スレッド)で CPU の再帰と同じ順に回し、
  段の間はグループのバリア。最も粗い段はいつも ImTail。
- 効果(release・RTX 3070 Ti): 熱い点の鋭い刻み 9.7〜11.5 → 4.0 ms・落ち着いた後 5.2〜5.5 → 2.1〜2.3 ms(V 1 回 0.57 → 0.24 ms)。
  鎖の案 a(レベル 3〜6)初め 1.95 → 1.65・後半 1.4〜1.5 → 1.07 ms/刻み。表は docs/tickets/T-0120-implicit-gpu-fixed-cost.md と docs/perf.md。
- 代案: 境を 8・32、ImTail を 256・2048 節にする(測って 16・1024 が速い。2048 は 1 つの SM に寄りすぎて逆転)/ Work Graphs(空の回のバリアは同じなので後回し)。
  空の回の 1 Dispatch あたり約 1 µs(バリア)は残る。さらに減らすなら止める判定と CycleEnd を 1 Dispatch に(最後のグループが判定)。

## 追記(2026-10-06、T-0119: 木の伝導へのつなぎ方。決めた人: Claude〔実装の細部〕。CPU。GPU は T-0127)
- **面は「流れを計算する側」のレベルで分ける**: 違うレベルなら細かい側、同じレベルなら両側のレベルが基準より細かい(Δk 1〜implicitMaxGap)面は
  陰解法、ほかは今までの陽解法(engine/src/sim/multires_implicit_conduction.cpp。MultiresStepOptions::implicitConduction、既定 false。maxSubcycleGap は 0)。
  面ごとにどちらか一方なので、保存は今までどおり面ごとに 1 つの値でビット単位。印・頁・端数の枠は陽解法の判定のまま。
- **境のセル**: 未知数は基準より細かいセル。その面の粗い側の基準以下のセルも系に入れ、境の面だけを陰解法で受ける(基準以下の面は陽解法 = 面で分けた分割)。
  断熱の境(T-0117 の見積もり)や、粗い側を刻みの初めの温度に固定する形より、粗い側も同じ式で受けるので速さが揃う。境のセルも安全網の範囲の判定に入る。
- **眠っている頁のブロックも系に入れる**: 陰解法は 1 刻みに遠くまで熱が届くので、活性で刻むブロックだけにすると全部刻んだ時と系が変わる(活性 = 全部が崩れる)。
  一様なブロック・凍らせたブロック・熱容量 0 のセルとの面は流れない(陽解法と同じ。一様なブロックは刻みの初めに隣と温度差が無い)。
- **熱容量は刻みの初めの値で線形に**: セルの温度・熱容量は MrCellThermal(整数部から)。試作のセルに「刻みの初めの温度」を持たせ、エネルギーは仮の値として
  足した後との差を変化の表へ(相変化・反応の分は次の刻みの温度に出る)。
- **Δk の上限 8**(implicitMaxGap): T* は mK × 2^16 の整数なので、面の流れの誤差は約 4^Δk × 2^-16 mK。Δk 24 まで陰解法にすると判定で止まらず上限 64 回まで回り、
  安全網が 14 万セルを陽解法に戻した(たくさんの要求の場面)。それより細かい所は陽解法のまま(遅い。判断待ち: T-0119 の (2))。V の上限は 64(D-436: 解き切る)。
- 影のブロック(覗き窓)は陽解法のまま(T-0128)。
- 結果: 物差し(基準の 8 セルと同じ長さの山)Δk 1〜5 で 0.988〜0.991・保存ビット一致・活性 = 全部・2 回一致。鎖の場面で V 初め 12 → 後 4〜5 回/刻み(系 1907 セル)。
  1 刻みより速く落ち着く短い山(1 ブロック)は後退 Euler の性質で 1 刻みの減りが遅い(Δk 4 で 0.37)→ 判断待ち T-0119 の (1)。

## 追記(2026-10-09、T-0154: 記録の形を刻みごとに選ぶ。決めた人: Claude〔実装の細部〕)
- **費用の元**: T-0136 の形は上限の段 × 上限の回を積む。止めた後の回は述語で Dispatch を飛ばしても、バリアは CPU が積んだ数だけ走る(述語はバリアに効かない)。
  熱い点(V 3 回で止まる・全部の段が ImTail)は 1 刻み 16 回 × 41 個の空の Dispatch + バリアが残った。GPU の側では記録を短くできないので、CPU が積む数を減らす。
- **記録の形(GpuImplicitRecordShape)を RecordStep に渡す**: 段ごとに積む段の数(dispatchLevels)と、最も粗い段の掃き出しを積むか
  (coarsestDispatch。積まなければ最も粗い段はいつも ImTail)。ImPlanArgs は同じ形で ImTail の境を切る。**どの形でも解いた値は同じ**
  (積まなかった段は ImTail の 1 グループが CPU の再帰と同じ順で回す。整数の和)。変わるのは費用だけなので決定性(ADR-0008)の外にある。
  既定(形を渡さない)は T-0136 と同じ。全部の段が ImTail の系は V 1 回 3 Dispatch(T-0135 までと同じ数)に戻る。
- **形の選び方(GpuImplicit::ShapeFrom)**: 前の刻みの GPU の数から。段は前の刻みで下りが止まった段まで(形で切る前の ImTail の境 = 計画の
  IM_PLAN_WANTED_TAIL。切った後の値を使うと、一度浅くした形が深い系に戻れない)、最も粗い段の掃き出しは前の刻みが ImTail を使わなかった時だけ。
  形が深くなった刻みは、その分を ImTail が回す(その刻みだけ遅い。次の刻みで追いつく)。CPU が読むのは費用の目安だけで、世界の状態は書かない
  (ADR-0001 改訂。遅れて読んだ数でもよい)。伝導の段から呼ぶ形(T-0132)でも同じ関数を使う。
- **捨てた形**: (a) dispatchLevels を場面の上限から決める(上限の大きさからは段ごとの節・隣の数が分からない)・
  止めた後の回を「ImTail が段 0 から全部」の安い回にする(試した。回が前の刻みより増えた刻みで大きい系を 1 グループで回す崖がある:
  たくさんの要求を全部 ImTail で回すと 1 刻み 9.7 → 71 ms。全部 ImTail の系ではもともと同じ数なので要らない)・
  (c) Work Graphs で V サイクルを回す(赤黒の掃き出しの間に全体の待ちが要り、Work Graphs には無い。最後のグループが次を起こす形は書き直しが大きい)。
  数は docs/tickets/T-0154-implicit-empty-dispatch.md。

## 追記(2026-10-09、T-0132: GPU の伝導の段から呼ぶ。決めた人: Claude〔実装の細部〕)
- **呼ぶ所**: GpuMultires::RecordConduction の最後の小刻みの流れの後・ConductApply の前(CPU の StepConduction が ComputeConduction の後に
  AddImplicitConduction を呼ぶのと同じ所)。陰解法の段は GpuMultiresImplicit(sim/gpu_multires_implicit。GpuMultires::EnableImplicitConduction
  で上限から作り GpuMultires が持つ): GpuImplicitBuild(凍った印を見る)→ GpuImplicitLevels(既定の積み方。LvTail は T-0147 まで使わない)→
  GpuImplicit(RecordReset → 系と段を写す → RecordStep)→ GpuImplicitBuild::RecordApply → GpuImplicit::RecordRelease。CPU の系は一度も写さない。
- **流れの段で飛ばすブロック**: CPU の InImplicitConduction と同じ判定を multires_conduct.hlsli の InImplicitConduction で。印は stepFlags に詰める
  (ビット 3 = 陰解法・ビット 5〜7 = implicitMaxGap − 1。ルート署名は 63 / 64 語で、定数を足さない)。そのため **GPU の implicitMaxGap は 1〜8**
  (既定 8。9 以上は FX_ASSERT。Δk 8 より細かい所はもともと陽解法のまま〔T-0119〕なので遊びは変わらない)。印の段(ConductMark)は飛ばさない(CPU と同じ)。
- **解いた変化を足す**: implicit_build.hlsl の BuildApply(1 スレッド = 系のセル 1 つ。u5 だけ GpuImplicit のセルのバッファに結ぶ)が
  「解いた後 − 刻みの初め」(刻みの初めは BuildCells と同じ式で熱容量と刻みの初めの温度から作り直す)と端数を伝導の変化の表へ 64bit の atomic で足す
  (AddConductDelta を multires_bindings.hlsli へ移して共有)。CPU は頁のブロックを全部 StepPagedBlock に通すので、活性の刻みでは変わったセルの
  ブロックを伝導の一覧へ足す(眠っているブロックも ConductApply が足す。刻む印は付けないので反応は進めない = CPU の react = false と同じ)。
- **伝導の段の Work Graph 版**(conductionGraph): 一覧の数は TreeFractions が見出しへ写した後なので、陰解法の刻みの足す段(ConductApply)だけ Compute で投げる。
- **同じリストに何刻みも積む**: GpuImplicit の RecordReset はバッファが COMMON の前提なので、刻みの終わりに RecordRelease で COMMON に戻す。
  記録の形は前の刻みの数(RecordCostReadback で読み戻した、遅れたものでよい)から ShapeFrom(T-0154)。
- **上限を超えた刻み**(系の未知数・セル・節・隣が GpuMultiresImplicitLimits を超える): 今は CPU と合わなくなる(系を作る段の overflow が立つだけ)。
  頁・端数の枠のように「足りなければ凍らせる」形にするかは判断が要る(T-0132 のチケットの「判断待ち」)。
