# ADR-0016 多重解像度の木の枠の番号も決定的にする(まず決定的に作り、速さが気になったら非決定的を考える)

- Status: Accepted
- 日付: 2026-10-04
- 決めた人: ユーザー(Claude が案を出した。T-0018 の着手時)

## 背景
- 疎な木(17 §5)はブロックの枠と端数の枠をプールから取り、要らなくなったら返す。同じ刻みに多数の細分/粗くする要求が並列に来る。
- GPU で空きの枠を atomic で取ると、どの要求がどの枠を取るかが実行ごとに変わる。世界の中身が同じでも配列の並びが変わるので、
  CPU リファレンスと配列のまま比べられず、状態のハッシュ・セーブ・デバッグは (レベル, 座標) の順に並べ直して作る必要がある。

## 決定
- **枠の番号も決定的にする**: 要求を要求の一覧の順に並べ、必要な枠の数の累積和で「空きのスタックの何番目を使うか」を決める。返すのも同じ(累積和の順に積む)。
  → ブロック・セル・端数・空きのスタック・帳簿を、CPU と GPU で配列のままビット一致させる。
- **索引(ハッシュ表)は見出しから作り直せるもの**として状態に入れない。並列の挿入で表の中の並びは変わってよい(引いた結果だけが一致すればよい)。
- 観察(影・世界の写し)の枠は世界の枠と別の範囲にする(覗いても世界の枠の番号が変わらない。D-403)。
- 速さが気になり始めたら(累積和の費用・要求の数の上限)、非決定的な割り当て(atomic)に変えることを考える(ユーザー、2026-10-04)。
  その時は世界のハッシュを (レベル, 座標) の順に作り直し、CPU との比較も並べ直してから行う。

## 検討した代案と、採らなかった理由
- 枠の番号は非決定的(atomic で取る): 速いが、上の比較・セーブ・デバッグが複雑になる。今は要求の数が少ないので後回し。
- 索引の表の中の並びまで決定的(Robin Hood など): 並列の挿入が難しい。引いた結果が同じなら並びは要らない。

## 影響
- 17 §5 に要求の処理の段(解決・確定・割り当て・適用・解放・索引の作り直し)を書いた。
- 要求を作る側は、要求の一覧を決定的な順に並べて渡す(コマンドは番号順。GPU で作る側は並べてから。T-0100 以降)。
