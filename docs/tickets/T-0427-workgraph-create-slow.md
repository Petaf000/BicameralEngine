# T-0427 試験の Work Graph の作成が場面ごとに 100 秒かかる原因を調べる(T-0426 から分けた)

- Status: Done
- 種類: 研究
- PC: 必須
- 見積もり: チャット 1 回分
- 設計: D-460(GPU の順番待ち)。関係: T-0426・T-0263

## 目的
debug の HW の gpu_multires_test で、場面ごとの Work Graph(「ワークグラフ Multires」)の作成が 95〜130 秒(多いと 384 秒)かかり、
試験の時間のほとんどになっている(2026-10-12 08:00〜09:00 の ctest)。同じ日 05:26 の run(--part wide)では作成込みで 1 場面 2〜20 秒だった。
WARP の作成は 6 秒。速い時と遅い時の差を突き止め、試験を速くする(GPU の順番待ちで他のランナーを止める時間が減る)。

## 試すこと(順に)
1. 同じビルドで、run(作業ディレクトリ bin)と ctest(out/build/<p>/tests)で --part wide-uniform を続けて流し、作成の秒を比べる。
2. 同じ場面を 2 回続けて作る(--repeat-wide uniform... 1 プロセスで 2 回)。2 回目が速ければドライバのキャッシュ、遅ければ毎回のコンパイル。
3. 他のランナーのビルド・CPU の試験と重なった時と、重ならない時で比べる(CPU の混み)。
4. 場面ごとに作り直さず、組の中で 1 つの GpuMultires を使い回せるか(試験の形を変える。CPU リファレンスとの比べ方は変えない)。

## 打ち切り条件
1〜3 で原因が分からなければ、4(使い回し)を試して終える。4 が試験の意味を変えるなら、作成の秒を docs/perf.md に残すだけにする。

## 分かったこと(2026-10-13。RTX 3070 Ti / 32.0.15.9597・i7-12700F)
- **重いのは Work Graph より Compute のパイプライン**。作成の時間をログに出した(gpu/creation_timer.h。壁時計とプロセスの CPU 時間):
  debug の溢れの場面(wide-uniform)の 1 回目で、Compute のパイプライン 35 本 55.2 秒(CPU 54.6 秒)+ Work Graph 8.7 秒(CPU 8.6 秒)。
  CPU 時間が壁時計とほぼ同じなので、**待ちではなくドライバのコンパイルそのもの**(CPU の混みで遅くなったのではない)。
- **run と ctest で違う**(同じビルド・同じ exe・同じ引数 `--queue compute --part wide-uniform --no-gbv`・debug):
  | 起動 | 作業ディレクトリ | 1 場面目 | 2〜4 場面目(同じプロセス) |
  |---|---|---|---|
  | `job.py run`(07:32) | out/build/debug/bin | 55.2 + 8.7 秒(新しいビルドで初めて) | 1.35 + 0.24 秒(キャッシュに当たる) |
  | `job.py test`(ctest。run の直後) | out/build/debug/tests | 55.6 + 9.0 秒 | **毎回 55.3 + 8.7 秒**(当たらない) |
  ctest から起動したプロセスでは、同じプロセスの中でも、直前の run がコンパイルした同じシェーダーでも、作るたびに全部コンパイルし直していた。
- 過去のログ(runner/logs。2026-10-11〜13)も同じ形: run は「1 回目だけ遅く(新しいビルド)、あとは 0.2〜2 秒」、ctest は「毎回同じだけ遅い」
  (release の溢れ 50〜54 秒・鎖 11〜12 秒・debug の溢れ 95〜125 秒)。2026-10-12 05:26 の「速い」と 08:00 の「遅い」の差は、run か ctest かの差で説明できる。
- 同じ時間帯の WARP(ソフトウェアのコンパイル)は 1.5 秒で作れていた。CPU の混み(候補 3)は主因ではない。
- ドライバのキャッシュ(%LOCALAPPDATA%\NVIDIA\DXCache)は 573 ファイル・23 GB(2026-10-13)。exe ごとのファイル(名前の末尾 8 桁)は
  run の後には書かれていたが、ctest の後には書かれていなかった(**ctest から起動したプロセスはキャッシュを読みも書きもしない**ように見える)。
- **作業ディレクトリは原因ではない**: GPU の試験の作業ディレクトリを bin にした ctest でも、1 回目は 56.1 + 9.1 秒(直前の run は同じシェーダーで 2.5 + 0.4 秒)。
  ctest の子プロセスの環境変数(LOCALAPPDATA)・対話型・セッションも run と同じだった。**ctest の起動の何が効いているかは未確認**(→ T-0455)。

## やったこと
1. **作成の時間をログに出す**(engine/src/gpu/creation_timer.h): 「ワークグラフ X: プログラムの作成 N ms(プロセスの CPU N ms)」・
   「多重解像度: Compute のパイプラインの作成 N ms」・1 秒を超えた Compute のパイプラインは .cso の名前も(どのシェーダーが重いか)。
2. **試験の中でパイプラインを使い回す**(打ち切り条件の 4): engine/src/gpu/pipeline_cache.h(作ったルート署名・Compute のパイプライン・
   Work Graph のプログラム〔状態オブジェクト〕を名前で覚える置き場)。`GpuMultiresOptions::pipelineCache`(無ければ今まで通り毎回作る)。
   WorkGraph を `CreateProgram`(コンパイル)と `Create(program)`(プロパティと裏のメモリ。グラフごと)に分けた。
   gpu_multires_test は既定で使う(`--no-pipeline-cache` で毎回作る)。使い回すのはコンパイルの結果だけで、バッファ・裏のメモリ・状態は
   場面ごとに新しく作る(裏のメモリの初期化も場面ごと)ので、CPU リファレンスとの比べ方は変わらない。終わりに「使い回した N 回・作った M 回」を出す。
   結果(debug・ctest): 1 回目はキャッシュに当たらず約 65 秒のまま、2 場面目からは刻みの時間だけ。wide_limits 86 秒・wide_overflow 84 秒・wide_many 122 秒・wide_uniform 70.5 秒(前は 259 秒)。
   run の wide-uniform は 4 場面で 6.3 秒(前は 72 秒)。数値は docs/perf.md。
3. 試した後に戻したもの: GPU の試験の作業ディレクトリを bin にする(効かなかった)。
