## 見つけたこと(T-0273、RTX 3070 Ti / 32.0.15.9597、release)
- RX_GPU_WIDE_SPECIES = 64 にすると、gpu_multires(HW)の「溢れを使う世界の刻み(伝導 あり)」(RunLimitsStepWide。上限の場面・12 刻み・
  1 刻みずつのリスト・毎刻み CPU と比べる)が DEVICE_HUNG。10-10 の 2 回と 10-11 の 1 回で 3 回中 3 回(10-11 は作ってから約 145 秒後。
  伝導なしの同じ場面は 1 秒で通る)。WARP は通る(10-10)。ログは wt4 の runner/logs/20261011-012602-test。
- 同じ場面を 1 つだけ流す(`gpu_multires_test --queue compute --diagnose-wide 1 --diagnose-limits --diagnose-conduct`。段ごとのタイムスタンプあり・
  CPU と比べない)と 1 刻み 4 ms(32 種で 2.5 ms)で 12 刻み通る。= 1 刻みの時間切れではない。前の場面(同じデバイスで先に走る場面)の後でだけ、
  またはタイムスタンプが無い時だけ止まる疑い。

## やること
1. 64 にして、--diagnose-wide に「伝導なしの上限の場面 → 伝導ありの上限の場面」を 1 つのプロセスで続けて流す・段ごとのタイムスタンプを切る・CPU と比べる、
   を足して、止まる組み合わせを絞る。
2. debug プリセット(GPU の FX_ASSERT・DRED)で同じ組み合わせを流し、LoadGpuWideCell の溢れの範囲(FX_ASSERT)・伝導の段の溢れの変種
   (512 スレッドが上限の無い形のセル約 800 B を持つ)に壊れた値が入っていないか見る。
3. 打ち切り条件: 1.5 時間で止まる段の見当がつかなければ、分かったことを書いて T-0272 の「伝導の段から上限の無い形のセルを無くす」を先にやり、直るかを見る。

## 引き継ぎメモ
- 再現(上限を 64 にしてから): `job.py run -Preset release -Exe gpu_multires_test -- --queue compute --repeat-wide many,many-conduct 1`
  (約 5 秒で DEVICE_HUNG)。通る対照: 同じ引数に `--repeat-fresh-queue`、または `--queue direct`。場面の名前は limits / limits-conduct /
  overflow / overflow-conduct / many / many-conduct。
- 原因の見当(未確認): D3D12 はコマンドリストをまたいで状態を持ち越さないので、残っているのはドライバーが compute キュー(コンテキスト)ごとに持つもの。
  一番疑わしいのはスレッドごとのローカルメモリ(スクラッチ。上限の無い形のセル RxGpuWideCell が 64 種で約 780 B、核の中で何個も持つ)と、その
  コンテキストの切り替えの退避。止まりは上限(= 1 スレッドのスクラッチの大きさ)が 48 → 56 の間で始まり、前の場面のデータ(32 種のセル)に依る。
  シェーダーの範囲外の書き込みの証拠は無い(同じ場面の繰り返し・direct キューは毎刻みビット一致)。NVIDIA の中は見えないので、これ以上は打ち切った。
- 直し方(T-0272 へ): 伝導の段から上限の無い形のセルを無くし(熱は溢れから直接足す)、大きいセルは少ないスレッドの段で刻む(またはセルを作業場の UAV に置く)。
  1 スレッドのスクラッチが 48 種相当より小さくなれば、この止まりの条件から外れる見込み。T-0272 の完了条件に「上限を上げた形で、HW の compute キューで
  `--repeat-wide many,many-conduct,limits,limits-conduct 3` が通る」を足すとよい(この再現は 5 秒で回る)。
- 本番の刻みも compute キュー(frame_loop の "Sim")なので、direct キューで通ることは逃げ道にならない(キューを替えるのは設計の方向。下の判断待ち)。
- 上限 64 の 1 刻み(計測の場面・伝導あり・1 刻みずつ・compute キュー・場面 1 つ): 最大 180 ms(足す段がほぼ全部)。時間切れではない。

  (反応の結果はどちらでも同じ。D-428 に触れない)。
