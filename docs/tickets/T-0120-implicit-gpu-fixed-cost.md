## 目的(1〜2 行)
T-0117 の GPU 版は、費用が「Dispatch の数 × 1 回の待ち」と「1 つの節の隣が 100 個を超える長い行を 1 スレッドで回す」ことで決まっている
(熱い点の V 1 回 0.6 ms・鋭い刻み 10.8 ms)。ビット一致を保ったまま、鋭い刻みを 5 ms 以下に近づける。

## 完了条件(チェックできる形で)
- [x] 長い行(隣が多い節。違うレベルの面の粗い側・粗い段)を複数のスレッド(ウェーブ)で足す。整数の和なので順によらず同じ値(04 R1)
- [x] 小さい段(節の数が 1 グループに収まる粗い段)の掃き出し・縮約・直しを 1 Dispatch にまとめる(groupshared とグループのバリア)
- [x] 止めた後の空の回の費用(今 0.91 µs/Dispatch。バリアが残る)を減らす方法を 1 つ試す(例: 上限まで積む代わりに回を束ねて間接の起動)
      → 試したのは「小さい段をまとめて V 1 回の Dispatch の数を減らす」(上の項目と同じ仕組み)。1 Dispatch あたりの空の費用(約 1 µs)は変わらない
- [x] gpu_multires_implicit_test が HW・WARP でビット一致のまま。計測の表(T-0117 と同じ)の前後を docs/perf.md に

## 何をしたか(形。決めたのは Claude〔実装の細部〕。ADR-0019 追記)
- **長い行をグループで**: 隣を足す段(掃き出し・縮約・止める判定)は「節の並び」(新しいバッファ u9)を回す。前の short 個は今までどおり 1 スレッド = 1 節、
  後ろの long 個(隣が 16 個を超える節)は 1 グループ(64 スレッド)= 1 節で、隣をスレッドで分けて足し groupshared の木で和にする。整数の和なので CPU と同じ値。
  掃き出しは色ごとに並びを分ける(その色の長い節だけグループに。ほかの色の節は写すだけ)。縮約は子の隣の最大で分ける。Dispatch の数は増えない。
- **小さい段から下を 1 Dispatch に(ImTail)**: 節が 1024 以下・隣が 32 以下の段から最も粗い段までの V サイクル(前の掃き出し・縮約・最も粗い段・直し・後の掃き出し)を
  1 グループ(1024 スレッド)で CPU の再帰と同じ順に回し、段の間は DeviceMemoryBarrierWithGroupSync。そういう段が無くても最も粗い段は ImTail(掃き出し 8 回 → 1 Dispatch)。
  V 1 回の Dispatch: 熱い点 70 → 43・鎖(全部)50 → 43・鎖(案 a)50 → 23・鎖(案 b)50 → 3・物差しの山 Δk 3 30 → 3。
- 調整(release・熱い点と鎖で測った): 長い行の境 8 / 16 / 32 → 16(32 は熱い点 2.42 ms・鎖(全部)3.67 ms と重い。8 は 16 と差が測れない)。
  ImTail の大きさ 256 / 1024 / 2048 節 → 1024(2048 は鎖(案 a)の初めの刻みが 1.64 → 1.97 ms と重い。1 グループ = 1 つの SM に仕事が寄りすぎる)。
