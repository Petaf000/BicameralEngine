## 事前調査(2026-10-09、調べ役。未確認の数値は「推定」「未確認」)

### 今の実装の要点
- 1 刻み = 1/60 秒(uint64)。熱①はレベル k を 4^σ 回の小刻み(σ = clamp(k − 基準, 0, Δkmax=3))、違うレベルの面は細かい側が計算し粗い側は小刻みの終わりに整数部 + 端数で受ける(ADR-0017)。粗い側の時間補間は無い。
- 細かい所(基準 + 1〜8)は陰解法②で 1 刻み 1 回(ADR-0019・D-434)。反応は全部の小刻みの後に 1 刻み 1 回。遅い反応は幾何分布の待ちで wakeTick まで眠る(ADR-0018)。放射は 1 刻み 1 回の前提(T-0028)、物理は小刻み 1、気体の案(T-0026)はレベルごとに 2^σ。06 §1 の「第 1 段: 全体で同じ細分」は設計だけ。
- GPU の固定費: 小刻み 1 回あたり約 50 µs(鎖の場面 8.4 ms/刻み。T-0111)。空の ExecuteIndirect 約 30 µs、空の Dispatch 0.9〜2.5 µs、Work Graph 版の空の小刻み 91 µs(Compute 版 19〜44 µs)。

### 結論(推奨): 2 の累乗の時間の段(bin)を全部の系で共有し、ブロック × 系ごとに段を決める Berger–Colella 型
1. 1 刻み = 2^B のマイクロ刻み(整数の時間線。GADGET/SWIFT の power-of-two time bins と同じ形)。系 s のブロックは段 b_s を持ち、マイクロ刻み t が 2^(B−b_s) の倍数で 1 歩進む。熱①: 段 = 2σ。熱②: 段 0。気体・水: レベルごとに +1 + CFL の基礎の段。
   **反応は段を負まで延ばす**: 負 = 今の待ち(何刻みも眠る)、0 = 1 刻み 1 回、正 = 爆発の小刻み。反応はセルの中で閉じていて面の流れが無いので、ブロックごとに勝手に小刻みにしても保存は自明。
2. 段は**刻みの初めの状態から整数で決め、その刻みの間は固定**(1 刻み遅れ・Jacobi 型)。最大は atomic max(順不同。R4)。刻みの途中で段を上げる形(SWIFT の起こし)は後の研究。段が足りない刻みも流出の比例の縮め・熱容量の上限で保存と正の値を守る。
3. 系どうしの受け渡しは全部「面の流れ = 段の細かい側が計算、粗い側はその歩の終わりに整数部 + 端数で受ける」(ADR-0017 を「レベル」から「段」へ)。1 マイクロ刻みの中の順は固定: 気体 → 熱 → 反応(Lie 分割)。放射は段 0(遠くの発熱源は負の段)、物理は島ごとの小刻みで別枠(M6)、セルとの結合は 1 刻み 1 回。
4. 06 §1 の第 1 段(全体で同じ細分)は飛ばす(熱がもうレベルごとに分けていて、R-LOOP-1 の基準〔1 か所が全体を重くしない〕にも反する)。

### 方式の比較
- レベルごと(Berger–Oliger / Colella): 全部満たし熱で実証済み。弱点は小刻みの固定費と、時間補間が無く境界の精度が 1 次なこと → 骨格。
- 非同期・イベント駆動(セルごとの時刻。DES): 整数の時刻なら決定的だが優先度付きの待ち行列と同時刻の順が要り GPU に向かない → 輸送には採らない(反応の待ちはこの形で合っている)。
- Osher–Sanders 型・SeisSol/EDGE の比 2 の clustered LTS: 推奨と同系統。CPU で 10 倍超の速さの報告。SeisSol の GPU 版は LTS の効率が「mediocre」と報告(固定費と同根の見込み)。
- multirate(MRI-GARK など): 1 次の整数の陽解法では得が小さい → 気体の音の小刻み(Q11-B。split-explicit)にだけ。
- IMEX: 熱②がすでにこれ。速い反応がマイクロ刻み 64 回を超えるなら、セルごとの陰解法(整数の後退 Euler・回数固定)か「瞬時に平衡へ進む規則」(R-REACT-1)。PeleLMeX は小刻みをやめて全レベル同じ刻み + 反応は BDF(閉じた部屋の圧力の扱いのため)→ 射影法の気体(T-0026 案 B)は小刻みとぶつかる警告。
- 重い所の時間だけ遅らせる: 境界で世界の時刻が食い違い D-208 に反する → 推奨しない(D-202 の遅れは世界全体。観察の枠 17 §4B・D-433 は今のまま)。

### GPU での組み方
- 費用は小刻みの回数 × 固定費。(a) 系を同じマイクロ刻みの段にまとめる (b) 頁・端数の枠の配り(TreeExpand・TreeFractions・Prepare)を小刻みの外へ出し、小刻み 1 回を印・流れ・終わりの 3 段に(目標 ≤ 15 µs・未確認)(c) 研究: 時間方向のタイル(temporal blocking。袖 g 幅を groupshared で g 小刻み続けて回す。両側が同じ入力から同じ整数の式なのでビット一致と保存は保てる見込み)。
- Work Graphs は全体の同期が無く深さ ≤ 32 → 小刻みは Compute の Dispatch の列、空の段は空で抜ける。小刻みの切れ目はフレームの切れ目にしてよい(ADR-0011)。

### 試す順番と、次の代案へ移る条件(D-411)
1. 工学: 時間線と段を CPU リファレンスに。熱だけ・段 = 2σ で今の T-0108 とハッシュ列がビット一致(入口)。
2. 工学: 反応の段(正の段の小刻み + 負の段 = 今の待ち)。600 K の木箱・爆発の場面で保存ビット一致・64 回以内で破綻しない。超えたらセルの陰解法 → 平衡の規則。
3. 工学: 段をまとめる・配りを外へ。条件: 鎖の Δkmax 3 が 5 ms 以下(T-0111 の目標)。届かなければ (c) と、②を広げる。
4. 気体(T-0026 G3)を 2 つ目の系として同じ段に載せ GPU とビット一致。粗い側から何度も引く時の正の値は、粗い側の出せる量を引く回数で割る(熱の C/8 と同じ)。
5. 研究: 状態で決める段・temporal blocking・刻みの途中で段を上げる・とても細かいレベルの気体を陰的な拡散/低マッハ数へ。段を状態で決めて保存が破れたら、レベルだけで決める形へ戻す。

### リスクと未確認
- 固定費をまとめた後の値は未測定。粗い側の時間補間が無いので気体の波がレベルの境で偽の反射を起こさないかは未確認(GAMER は 2 時刻で時間補間)。熱と反応の分割の順が着火の時刻に与える誤差・粗い側から何度も引く時の正の値・AMD(D-207)も未確認。
- 「時間方向の細分の得は少数の点だけを深く細かくする時に大きい」(astro-ph/0310891)。このエンジンの使い方はまさにその場合だが得の大きさは未測定。
- ゲームの事例(Minecraft の流体の予定 tick〔溶岩 30 tick/ブロック〕・UE の Animation Budget Allocator)は保存・決定性の意味の局所時間刻みではない。物理として正しい局所時間刻みを持つゲームの例は見つからなかった。
