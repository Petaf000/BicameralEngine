## 目的(1〜2 行)
CPU の試作(time_step_tree)が 1 出来事に組む系(SpanSystem = 未知数 δ・節の容量・面の係数 × N・地面・反応の熱・値 0 を固定した外の面)を、
C-0 の GPU 版(GpuEquilibrium)で解き、CPU の SolveEquilibrium とビット一致を確かめて、1 出来事の時間と 1 セルの ns を V 1・V 2 で測る(T-0951 の気体からの見積もりの置き換え)。

## 作りの見立て(読んだ所: engine/src/sim/gpu_equilibrium.{h,cpp}・shaders/sim/equilibrium.hlsl・equilibrium_core.hlsli・gpu_equilibrium_block.h)
- GpuEquilibrium は段 0 を法則のシェーダーが組む形(気体は gas_projection.hlsl が EqGpuFinishNode・EqGpuSetRhs を呼ぶ)。熱の試作の段 0 は CPU が組んでいるので、
  **段 0 を写すだけの法則の段**(新しい `shaders/sim/equilibrium_upload.hlsl`: 節ごとに容量〔FxU128〕・6 面の隣と係数〔FxU128〕・右辺の項〔EqSourceTerm の形〕を
  バッファから読んで EqGpuFinishNode・EqGpuSetRhs を呼ぶ)と、それを積む小さな口(試験の中か `sim/gpu_equilibrium_upload.{h,cpp}`)を作る。部品(GpuEquilibrium・GpuImplicit)は変えない。
- 段の形は CPU の BuildImplicitGrid(SolveEquilibrium の中と同じ)で作って RecordUpload で写す。同じレベルの木(0.5 m の根だけ。単位 4 m = ブロック)なら今の GPU 版の範囲
  (違うレベルの節は T-0939)。
- GpuEquilibriumBlock(段 0 の係数を写せる k = 1 の版)も候補だが、CPU の参照が SolveEquilibriumBlocks で試作の SolveEquilibrium と違うので、ビット一致の相手にならない。
- 試験: `gpu_time_step_span_test`(新規)。試作の火事(shape=fine)を CPU で進め、決めた刻み(着火の後・前線の途中など 8 か所)の e = 0 の系を取り出して GPU で V 1・V 2 で解き、
  値 δ を CPU と比べる(ビット一致)。時間は GPU の時刻印(式〔写した段 0〕・段の重み・V・読み戻しを除く)を 8 回の最小で。系の大きさは 1 出来事のセルの数(約 600〜1,300)。

## 結果(2026-10-25・RTX 3070 Ti・release・compute キュー・`--no-gbv`・暖機 2 回の後 8 回の最小)

### ビット一致
- 系: 火事(0.5 m の根だけ = 同じレベル。4 m の単位)の e = 0 の系 8 つ(着火の 1・16・64・256・512・1024・2048・4000 刻み後の最初の 1 刻みの系)と、
  着火の 256 刻み後からの e = 1・2・3・5 の系 4 つ。木 `fine`(4,096 セル)で 512 節・`bigfine`(6.6 万セル・y・z に 16 m)で 8,192 節。
- V 1・V 2・e の表の回数(この場面では全部 V 1 か V 2)で、δ = 0 から解いた値が節ごとに CPU とビット一致(12 系 × 2 通り × 2 つの木)。
  e > 0 の系は前線の外(右辺がちょうど 0 = δ も 0)。e > 8 の系(V 2)は着火の後の 4,000 刻みには出なかった(前は V 2 で一致を確かめた)。
- **e = 0 の系は段 1 つ**(粗い段が要らない。熱容量 ≫ 面の係数)。V 1 = 最も粗い段の掃き出し 4 回。段の重み = 段 0(対角・重み・右辺)だけ。

### 1 出来事の費用(段 0 + 段の重み = 「重みは毎回」・D-648 の形。V の記録の形は前の解きから〔ShapeFrom〕)

| 512(fine の系) | 0.0133 ms | 0.026 ms | 0.052 ms | **0.040 ms**(78) | 0.065 ms | 0.100 ms |
| 1,024(512 を 2 つ並べた) | 0.0133 | 0.041 | 0.083 | 0.054 ms(53) | 0.096 ms | 0.115 |
| 2,048(4 つ) | 0.0133 | 0.038 | 0.076 | 0.051 ms(25) | 0.089 ms | 0.104 |
| 8,192(16 個) | 0.0195 | 0.042 | 0.082 | 0.062 ms(7.5) | 0.101 ms | 0.110 |
| 8,192(bigfine の系) | 0.11〜0.24 | 0.15〜0.28 | 0.25〜0.47 | **0.26〜0.52 ms**(32〜63) | 0.37〜0.71 ms | 0.49 |

| 524,288(64 個) | 1.44 | 1.02 | 2.03 | **2.46 ms**(4.7) | 3.47 ms | — |
- 大きい所の傾き: 段 0 + 重み 2.5 ns/セル・V 1 回 1.9 ns/セル。VRAM は 52 万セルで 364 MB(694 B/セル。部品の上限の形と 128bit の作業の語)。
- **揺れ**: 同じ bigfine の 8,192 の系が回によって 0.26〜0.52 ms(同じ回の中でも系の順に 0.26 → 0.30 ms と増えた = GPU の時計の見込み)。
  512 の系を 16 並べた 8,192 は 0.062 ms で、bigfine の 8,192 より 4〜8 倍速い(段 0 の段だけで 0.02 対 0.11〜0.24 ms)。系の形の違い(枠をまたぐ面・項の値)か時計か未確認 → T-1140。
- 記録の形を既定(段ごとの Dispatch 8 段)のままにすると小さい系の V が 2〜4 倍遅い。本物の GPU 版は前の解きの数から選ぶ。
- 段の重みの使い回し(`reweight = false`)は V だけの列。ただし段 0 には右辺(毎刻み変わる)も入っているので、使い回しで減るのは表の「段 0 + 重み」の一部(対角と重みの 128bit の割り算 6 回 / 節。右辺の項は約 8 回 / 節)。

### 火事 18 分の GPU の待ち(T-1090 の見積もり 11〜14 秒を置き換える)
- `time_step_tree_test fire-cost shape=fine`(0.5 m の根だけ・4,096 セル・既定 = 予算 0.1 K・緩衝なし・単位 4 m・e ≤ 8 は V 1): 出来事 53,246・解いたセル 0.85 億・
  最も大きい出来事 4,096 セル(CPU 190 秒)。実際の出来事ごとに解いた列を 1 本の系にまとめ、上の費用の式(TimeTreeSolveCost)で足すと:
  **大きい出来事の下限 0.52 ms で 13.9 秒・0.26 ms で 7.5 秒・0.062 ms(並べた系の値)で 2.7 秒**(1,024 セルを超える出来事 約 2.5 万・それ以下 約 2.9 万)。
  どれも 30 秒の線の内(ADR-0390)。既定は 0.26 ms(7.5 秒)にした。
- 広い世界の火事(ADR-0468: 6.4 万セルの角の火事 18 分・解いたセル 4.97 億)は傾き 4.4 ns/セルで約 2.2 秒 + 出来事の固定費(5.3 万 × 0.26〜0.52 ms = 14〜28 秒)= 16〜30 秒の見込み(未確認。
  1 m のセル = 違うレベルの木は今の部品の GPU 版で解けない = T-0939)。

### 早送りの待ちの見積もり(D-650・ADR-0472)
- `EstimateTimeTreeForward(setup, world, ticks, cost)`: 今の枠ごとの e が続くと見なして、出来事の組(2^j の倍数の刻み)ごとに解く列のセルと V を数え、費用の式で待ちを出す。
- `time_step_tree_test forward-estimate shape=fine`: 着火の 256・2048 刻み後から 1,024・8,192 刻みを見積もり、実際に進めた解いたセルと比べて **0.90〜1.00**
  (前線が広がる分だけ少なく出る。出来事の数は一致)。8,192 刻みの GPU の待ちの見積もり 1.3 秒(1 出来事 1,020 セル = 小さい出来事の形)。

## 土台に足りないもの(司令塔へ)
- 部品の GPU 版は V の回数を作る時に決める(`GpuEquilibriumOptions::solver.cycles`)。e ごとに V を変えるため、口は cycles = 1 で作って RecordSolve を回数だけ呼ぶ(値は同じ・ctest で確認)。
  部品に「この解きの V の回数」を渡す口があれば余分な Dispatch(計画の段)が減る見込み(足していない)。
- 段 0 の 128bit の割り算(EqGpuFinishNode の重み 6 回・EqSourceTerm の EQ_ROUNDING_WEIGHT の重み 1 項 1 回)が段 0 の費用の大半の見込み(未確認 = T-1140)。部品の共通の関数なので変えていない。
