## 目的(1〜2 行)
1 刻みの Dispatch が長い(25 ms 以上)と、描画はシミュを待っていないのに fps がシミュのバッチの速さまで落ちる(T-0004)。
原因を確かめ、描画が 30fps 以上を保てる「シミュの投げ方(分ける単位の長さ・分け方)」を決める。T-0012 のループの投げ方はこれに従う。

## 完了条件(チェックできる形で)
- [x] 重い刻みを k 個の Dispatch に分けて投げる試験の口(`--sim-split k`・`--split-submit`・`--pieces-per-frame p`)。分けても世界の結果は変わらない(gpu_probe_sim のテストが通る)
- [x] 分けた単位の長さ(ms)× 分け方(1 本のリストの中 / 別々の投入)× 描画の fps・描画の GPU 時間・世界の刻み/秒 の表を docs/perf.md に
- [x] 原因の仮説(GPU が compute と描画を同時に走らせず、Dispatch の切れ目でしか描画に替わらない、など)を測定で確かめて 06 の R-LOOP-2 に書く
- [x] 投げ方の決定(単位の目安 ms・分け方)を 06 §4 に書き、T-0012 がそれに従うようにする。方針ならユーザーに確認して ADR

## 研究の打ち切り条件(研究のときだけ)
D-411 により時間では打ち切らない。代案の順:
1. 1 本のリストの中で Dispatch を細かくする(UAV バリアで区切る)
2. 別々の ExecuteCommandLists に分ける(OS のスケジューラが間に描画を入れられるように)
3. 描画のキューの優先度・フェンスの入れ方を変える
4. (1〜3 で足りないとき)1 回の投入の GPU 時間を上限で切る(TickPacer が単位の数を決める)
どれでも 30fps を保てないと分かったら、原因を書いてユーザーと判断する。

## メモ・参考
- T-0004 の測定(docs/perf.md 2026-09-30): 12 ms/刻みで 103 fps、25 ms/刻みで 40 fps、34〜46 ms/刻みで 23 fps(HIGH で 30)。
  「刻みの間の隙間にだけ描画が入る」と考えると数が合う(12 ms × 60 刻み = 715 ms/秒が塞がり、残りの隙間に約 1.7 フレームずつ)。未確認の仮説。

## 作業ログ(チャットごとに 3〜5 行、新しいものを下に)
- 2026-09-30(1 チャット目): 重さを別の Dispatch(Busy)に分け、リストの中 / 別々の投入 / 1 フレームに p 個、を切り替えられるようにして測った(docs/perf.md)。
  原因は「描画は compute に先に積まれた仕事が終わるまで始まらない」(分けても・別々に投げても・vsync や優先度でも変わらない)。CPU が 1 フレームに予算ぶんだけ投げると戻る。
- 決定: ADR-0011(1 フレームの予算ぶんずつ投げる。目標 fps は設定、既定 60)。06 §4・§4.2・R-LOOP-2 に結論を書いた。
- ハマり: 同じコマンドリストを、キューのフェンスが前の実行を越える前に投げ直すのは誤り(debug layer [553]。release では黙って走る)。1 個ずつ別のリストにした。
  GPU 側で未来の描画のフェンスを待たせる形は、この誤りと一緒に試して固まった(正しい形では未確認)。
