# T-1078 物の熱の GPU 版の食い違い(物の中の伝導率の下ごしらえ)を直して CPU とビット一致させる(T-1064 から分けた)

## 目的(1〜2 行)
gpu_object_heat の段ごとの切り分け(刻み 1 を段ごとに流して比べる。RunStageCheck)で、① 下ごしらえの物の中の伝導率(OhVolumeConductivity)だけが CPU と食い違う。
直して、② 以降(流れ・物ごとの和と端数・セルへ当てる・反応)と 60 刻みのビット一致を通す。

## 分かっていること(2026-10-24 wt5)
- ① の温度・熱容量は一致。② の対の面の流れ・③ の粗い量・④ のセルも一致(物の中の伝導率を使うボクセルの熱だけがずれる)。
- 同じシェーダーの中で同じループを書き直して中間の値(気体の量 5,200,000・気体の重み 136,292,000・固体の体積 1,600,828・モル体積 108,094・伝導率 120)を書き出すと
  **全部 CPU と同じ**。正しい答えは 26 mW/(m·K)。それなのに OhVolumeConductivity の戻り値は 804,017(最後の割り算を 64bit の / で)・27,291,369(FxDivU128By64 で)と、書き方で変わる。
- 定数の書き方: 32bit を超える定数(OH_BOX_MM3 = 0.125 m³ など)は FX_U64 にした。DXIL の asm(out/build/release/shaders/asm/sim/object_heat_prepare.asm)の式は正しく見える。
- 疑い: 64bit の定数との比べ・選ぶ(min)か 64bit の積がドライバで食い違う。次に試す順: (1) 最後の式を「condensedMm3 ≥ 箱 なら 0」の形と FxMulU64Full + FxDivU128By64 に、
  (2) 箱の体積をルート定数で渡す(定数を畳ませない)、(3) 中間の値を作業場に持って別の段で割る。打ち切り: 3 つで揃わなければ、asm と DXIL の差を書いて司令塔へ。
