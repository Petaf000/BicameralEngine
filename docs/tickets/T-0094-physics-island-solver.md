# T-0094 物理: 島ごとに 1 グループで解く(全体の同期を減らす)を作り、今の方式と測って比べる

- Status: Done(2026-10-03。島の方式は CPU とビット一致したが遅いので採らない。使わない色を述語で飛ばすのは採った)
- 種類: 工学(測った結果で採るか決める)
- PC: 必須
- 見積もり: チャット 1〜2 回分(大きければ「島分け」と「島ごとの解」で分ける)
- マイルストーン: M1 の直後(docs/plan/ROADMAP.md の M2 の先頭)
- 設計: docs/design/08-bodies-physics.md §2・§6「結果(T-0092)」/ ADR-0002「計測」/ D-302

## 目的(1〜2 行)
接触でつながった物の集まり(島)ごとに 1 グループが、色の順番と反復をグループの中の同期だけで回す方式を作る。
今の「色ごとに全体で同期」(1 刻み約 180 回の Dispatch)と、結果がビット一致のまま、どれだけ速くなるかを測って採るか決める。

## 考え方(2026-10-03 の会話の要点)
- 島どうしはその刻みの拘束を共有しないので、島ごとに別々に解いても近似にならない。色の順番・反復の回数・6×6 の解き方は今と同じ → CPU とビット一致を保てる。
- 弱点は大きな島(崩れる城で何百個も触れ合う): 1 グループ = GPU の 1 区画でしか動かない。上限を超える島は今の全体同期の方式に回す 2 段構え。
- 島の数と大きさは実行時に決まるので、Work Graph(島ごとに、島の大きさに合わせたグループを起動)と相性がよい。眠り(T-0044)も島の単位で扱える。

## 完了条件(チェックできる形で)
- [x] 島分け: 接触(組)から、物がどの島に属するかを GPU で決定的に求める(実行順に依存しない。CPU の参照と一致)
- [x] 島ごとの解: 1 グループが島の物を色の順に、反復をグループ内のバリアだけで回す。上限を超える島は今の方式。3 場面の全部の刻みで CPU とビット一致・2 回の実行で一致
- [x] 大きな島の場面(例: 物 数百が全部触れ合う)を足し、上限を超える場合の切り替えを確かめる
- [x] 今の方式(T-0092: 1 刻み 質量比 1.9・積み木 2.6・山 3.75 ms)と比べる。Compute(島ごとに Dispatch)と Work Graph(島ごとのノード)の両方を測る(D-302)
  → Compute で測った。Work Graph 版は中身が同じで起動の形だけが変わり、遅さの原因(1 グループの中の 6×6 の待ち時間)が変わらないので作らなかった(ADR-0002「計測(T-0094)」)
- [x] (T-0093 から。2026-10-03 ユーザー決定)使っていない色の起動を無くす(島の中で使う色だけ回す。山では 16 色のうち 11〜12 色が空、1 刻み 0.3〜0.4 ms の見込み)。今の方式に回す大きな島の側も、空の色を起こさない形を検討する
- [x] 速くなれば採る。ならなければ採らない理由と数字を ADR-0002 / 08 §6 に残す

## メモ・参考
- 今のパスの内訳と計測の方法: `gpu_physics_test --profile`(T-0092)。
- Work Graph のノードの局所の変数は約 5〜6 KB まで(ADR-0002「計測」)。島の物の 6×6 は共有メモリに置く想定(1 物 336 B)。
