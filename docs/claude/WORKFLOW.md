# Claude と一緒に開発する仕組み — 詳細設計

このリポジトリを Claude(claude.ai のプロジェクト + デスクトップアプリで PC にリンク)と共同で開発するための設計書。
NMSWebViewer で使っているランナー方式を、長期開発向けに作り直したもの。

---

## 1. 全体像

```
 ┌──────────── claude.ai プロジェクト「Bicameral Engine」 ────────────┐
 │ 指示(project-instructions.md) + スキル bicameral-start            │
 │ チャット 1 つ = チケット 1 つ                                       │
 └───────────────┬───────────────────────────────────────────────────┘
                 │ デスクトップアプリでリンク(remote-devices)
 ┌───────────────▼────────────── ユーザーの Windows PC ──────────────┐
 │ H:\BicameralEngine  (git リポジトリ・VS2026 で「フォルダーを開く」) │
 │   ├ CLAUDE.md / HANDOFF.md / NEXT.md   ← Claude の記憶はここ        │
 │   ├ runner\runner.ps1  ← ユーザーが起動。鍵を表示                    │
 │   │   queue\ → 署名確認 → 実行 → logs\*.result.json(要約入り)     │
 │   └ scripts\jobs\  build / test / run / git / env                  │
 │                                                                     │
 │ device_bash(Linux 側): $HOME/mnt/BicameralEngine で読み書き        │
 │   ~/job.py(= runner_submit.py)で署名してキューに置き、結果を待つ  │
 └─────────────────────────────────────────────────────────────────────┘
```

**Claude はビルドも git も直接は実行しない。** ファイルを編集し、ジョブを投げ、要約を読む。
PC 上で実際にコマンドを走らせるのは、ユーザーが自分で起動したランナーだけ。

## 3. ランナー(runner.ps1)の設計

### NMS 版から変えた点と理由
| 変更 | 理由 |
|---|---|
| 鍵は固定。置き場所はリポジトリの中の git 管理外(`<リポジトリ>\.bicameral-runner\key.txt`。2026-09-30 に %USERPROFILE% から移した) | ユーザーは鍵を貼らない。リポジトリのフォルダを接続すれば Claude が自分で読める(ホームのフォルダの接続は自動の許可判定で拒否されることがあった)。「ランナー起動中」かつ「リポジトリのフォルダを接続したチャット」が実行できる |
| heartbeat.json に鍵 ID(SHA-256 の先頭 8 桁)を出す | Claude が投入前に鍵の食い違いを検出できる(拒否されてから気づくのを防ぐ) |
| 同じ署名のジョブは 1 セッション 1 回 | done/ から queue/ へのコピーによる再実行を防ぐ |
| `$env:JOB_OUT`(runner\out\<job>\) | スクショ・計測結果・キャプチャの置き場所を決めておく |
| result.json にエラー候補と末尾 60 行 | Claude がログ全文を読まずに済む = コンテキスト節約の要 |
| `-MaxHours N` で自動停止(既定は無制限)、`-RotateKey` で鍵を作り直し | 閉じ忘れが気になる日だけ時間を付ける。鍵が漏れた気がしたら作り直す |
| .part で書いてから .ps1 に改名(投入側) | 書きかけのファイルを拾わない |

### 変えていない点
HMAC-SHA256 署名 / 管理者で起動したら終了 / 1 つずつ時間制限付きで実行 / 署名不一致は rejected へ隔離。

### 守っていること・守っていないこと
- 守る: 接続フォルダに書き込めるだけの第三者(や、誤って置かれたスクリプト)がコードを実行すること
- 守らない: 鍵を持っている Claude 自身の誤り。これは git ジョブの拒否リスト(push / reset --hard / clean など)、
  作業ツリーの確認、小さいコミットで被害を小さくする。ランナーはユーザー権限で動くので、PC の他のファイルにも
  理論上は触れる。**鍵フォルダの接続を許可するのは、そのチャットで作業してほしいときだけ。**
  リポジトリだけを接続したチャット(設計の相談や NMS の作業中に誤って開いたなど)は、ファイルは読めても実行はできない。

### ジョブの種類
| コマンド | 中身 | 既定の上限 |
|---|---|---|
| `job.py check` | heartbeat と鍵 ID の確認だけ(ジョブは投げない) | — |
| `job.py env` | OS・GPU・ドライバ・VS・ツールの確認 | 30 分 |
| `job.py build [-Preset release] [-Clean]` | VS 開発者環境 → cmake --preset → build | 40 分 |
| `job.py test [-Filter x]` | ctest | 30 分 |
| `job.py run [-Preset p] -- <args>` | エンジン実行。スクショ等は JOB_OUT へ | 10 分 |
| `job.py git <args>` | git(破壊的操作と push は拒否) | 30 分 |
| `job.py raw <file.ps1>` | 任意スクリプト(最後の手段) | 30 分 |

## 4. チャットのライフサイクル

```
[開始]  ユーザー: ランナーを起動しておき、「続き」
   → bicameral-start: フォルダ 2 つの接続(リポジトリ・鍵)→ 鍵を読む → job.py check
   → CLAUDE.md → HANDOFF.md → NEXT.md → 該当チケットだけ読む
   → 「今の状態と、このチャットでやること」を 2〜3 行で返して着手

[作業]  編集 → build → test/run → 要約を読む → 直す …
   → 区切りごとに HANDOFF.md を更新(チャットが突然切れても失わない)

[区切り] 次のどれか
   ・チケット(機能)完了 ・方向転換 ・ユーザーの「引き継いで」(ツール呼び出しの回数では区切らない)
   → HANDOFF.md / チケットの作業ログ / NEXT.md → コミット
   → 「新しいチャットで『続き』と送ってください」
```

### なぜ「チャットの長さ」を回数で決めるのか
Claude は自分のコンテキストの残量を正確には測れない。長いチャットでは古い指示の効きが弱くなり、
読んだファイルの中身と今のファイルの中身がずれていく。だから「回数」「完了」「重さ」という外から判断できる基準で区切り、
記憶はチャットではなく**リポジトリのファイル**に持たせる。

### 記憶の置き場所
| 何を | どこに | 理由 |
|---|---|---|
| 変わらない運用ルール | CLAUDE.md | 毎チャット最初に読む |
| いまの状態 | HANDOFF.md | 1 画面で読める長さに保つ(上書きする) |
| 次にやること | NEXT.md | 順番付きのリスト |
| 作業の履歴 | チケットの作業ログ + git log | 追記していく |
| 決めたこと | docs/decisions/(ADR) | なぜそう決めたかを残す |
| 設計 | docs/design/ | サブシステムごとに 1 枚 |
| 計測 | docs/perf.md | 比較できる形で |

claude.ai のメモリには頼らない(メモリはチャットの要約なので不正確になりうるし、鍵が紛れ込む心配もある)。

## 5. 設計チャット(PC に触れない時間)

勤務中など PC に触れない時間は、スマホの Claude アプリで同じプロジェクトの「設計チャット」を開く。
- ファイルは読まない。反応表やゲームデザインを会話で詰める。
- 最後に Claude が「反映用まとめ」(どのファイルのどこに何を書くか)を出す。
- 次の PC チャットで「前の設計チャットの結論を反映して」と頼む。Claude はプロジェクト内の過去チャットを検索して拾える。
  拾いにくいときは、まとめを docs/inbox/ に貼っておく。

T-0002(反応表)はこの形で進めるのに一番向いている。

## 6. Visual Studio 2026 から見る・触る

- **開き方**: VS2026 →「フォルダーを開く」→ リポジトリのルート。CMakePresets.json を読んで自動で configure する。
- **構成**: ツールバーで `debug` / `profile` / `release` を選ぶ。
- **実行**: スタートアップ項目に `bicameral.exe` を選び、デバッグ引数に `--caps` など。
  `.vs/launch.vs.json` はユーザーごとの設定なので git に入れない(.gitignore 済み)。
- **Claude の文書を読む**: CLAUDE.md・HANDOFF.md・docs/ は VS の Markdown プレビューで読める。
- **同時編集の注意**: Claude がファイルを編集中に VS で同じファイルを編集すると上書きし合う。
  Claude は大きい変更の前に `git status` を確かめる。ユーザーが自分で編集したら、コミットしておくか一言伝える。
- **ビルドフォルダの共有**: ランナーのビルドと VS のビルドは同じ `out\build\<preset>` を使う。
  片方でビルド中にもう片方でビルドしない。

## 7. うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| `job.py check` が「鍵 ID が一致しません」 | job.py が古い鍵(BICAMERAL_KEYFILE・~/.bicameral-runner-key)を見ている。消せばリポジトリの key.txt を読む。それでも合わなければランナーを起動し直す |
| 「heartbeat.json がありません / 停止しています」 | ランナーが起動していない。起動するだけでよい |
| ジョブが rejected | 鍵が作り直された / ファイルが途中で変わった / 同じジョブの再実行 |
| Claude が「PC のファイル操作ツールが無い」と言う | そのチャットで device_bash がまだ使えない。もう一度メッセージを送るか、デスクトップアプリでチャットを開き直す |
| build が VS を見つけられない | `job.py env` で VS と vcpkg の場所を確認。VCPKG_ROOT を設定 |
| run でウィンドウが出ない / 止まらない | ユーザーがログオンしていないと描画できない。上限時間で止まる |
| Claude がファイルを見られない | チャットが PC にリンクされていない。デスクトップアプリでそのチャットを開いてメッセージを送る |
| Claude が同じエラーを繰り返し直している | 「いったん止まって、仮説と試したことを 5 行で」と頼む |
