# COMMANDER.md — 並走の司令塔のやり方(2026-10-10〜12 の運用から)

ユーザーが「続き」「並列で進めて」と言った時、1 つのチャット(司令塔)が作業役(サブエージェント)を作業ツリーごとに 1 体ずつ起こし、
報告を受けてマージし、次の巡目を起こす。司令塔はコードをほとんど書かない(マージの衝突の解消と小さな直しだけ)。

## チャットの初めに(2026-10-12 に読み落とした)
- **プロジェクトの文書(claude.ai のプロジェクトの claude/ の最新の指針)と NEXT.md の日付を比べる。NEXT より新しい指針があれば先にそれを読み、
  リポジトリに未反映なら、反映を最初の仕事にする**(2026-10-12 は claude/22 の指針 D-462〜D-471 を読み落としたまま、古い NEXT の順で 2 巡を回した)。
- 着手の順は ROADMAP の「今の順」(D-471。① 〜 ⑦)。古い M2・M3 の表の上から取らない。

## 場所とランナー
| 作業ツリー | 場所(Linux 側) | ランナー |
|---|---|---|
| 本体(main) | `$HOME/mnt/BicameralEngine` | `python3 ~/job.py ...`(BICAMERAL_ROOT なし) |
| wt2〜wt6 | `$HOME/mnt/BicameralEngine/.worktrees/wtN` | `BICAMERAL_ROOT=$HOME/mnt/BicameralEngine/.worktrees/wtN python3 ~/job.py ...` |

- 各作業ツリーに専用のランナーがある(`.worktrees/wtN/.bicameral-runner/start-runner.cmd` をユーザーがダブルクリックで起動。初回に鍵を作る)。
  止まっていたら起動だけを頼む。heartbeat はジョブの最中は更新されない(runner/running とログの時刻で見る)。
- 作業ツリーを足す: `job.py git worktree add .worktrees/wtN -b <branch> main` → `.bicameral-runner/start-runner.cmd` を wt4 から写す → ユーザーに起動を頼む。最初のビルドは vcpkg で 30 分ほど。
- **GPU の順番待ち**(D-460): scripts/jobs/test.ps1・run.ps1 は GPU を使う仕事を全部のランナーで 1 本ずつにする(名前付きミューテックス)。
  ビルドと CPU だけのテストは並走のまま。1 本が長い(release の GPU 40 本で約 1 時間)と全員が待つので、GPU の大きい組は分けて投げ、上限は短めに。
  `raw` は待たないので GPU を使う確かめは run か test で。
- **run は既定で GBV が付く**(ctest の試験は付かない)。多重解像度・溢れの HW の run は `--no-gbv` を付ける(T-0384。前の巡目の 85 分の止まり)。
- 待ち時間の目安(2026-10-12 その 3): 1 本の GPU の試験に、ほかの作業ツリーの組の後ろで 8〜21 分待った。GPU の組は 4〜8 本ずつに分けて積む。

## 巡目の回し方
1. 各作業ツリーの状態(`git status -b`・runner の queue/running)を確かめる。
2. 割り当てを決める: 本体 = 「前の巡目のマージの確かめ・記録(HANDOFF・NEXT・ROADMAP・QUESTIONS・DECISIONS)・push」+ 小さめのチケット。
   wt2〜wt6 = 1 チケットずつ。同じファイルを触りそうな組(例: GPU の溢れの 2 本)は、プロンプトにお互いの存在と触る所を書く。
3. Agent を 6 体、1 つのメッセージで同時に起こす(下のひな形)。3 時間 20 分後の見回りを send_later で予約する(止める時は消す)。
4. 報告が揃ったら、司令塔が main で `git merge --no-ff <branch>` を順に。衝突が文書だけなら両方残す(ADR の「追記 N」が重なったら後ろを N+1 に)。
   コードの衝突は意味を読んで解くか、その作業役の作業ツリーで載せ直させる。自動で合わさった所も、同じ仕組みを 2 本が触っていたら次の本体の作業役に「意味として合っているか」を確かめさせる。
5. 本体の作業役が確かめ・記録・push をする間に、ほかの作業ツリーは次のチケットへ(main の最新から `git switch -c t-XXXX main`)。

## 作業役のプロンプトのひな形(要点。過去の巡目のものを短くした)
- 役割: 「司令塔から 1 チケットを任された作業役。ユーザーとは話せない。最後の返答は司令塔だけが読む。日本語」。
- 環境: ToolSearch で device_bash などを読み込む / 作業ツリーの場所・ブランチの作り方 / ほかの作業ツリーは読むだけ(誰が何を触っているか)/
  device_bash は 30 秒前後で切れる(sleep 28 秒・編集はスクリプトにして当たったか確かめる)/ ランナーへは `timeout 25 ... --timeout <長め>` で投げてログを見る /
  .part が残ったら _to_delete/ へ / コミットのメッセージは runner/ のファイルを `commit -F` / 鍵を読まない / GPU の順番待ち / 新しいチケット ID・ADR の番号の範囲(作業役ごとに重ならないように司令塔が配る)/ 2 時間の約束。
- 並走の引き継ぎ: HANDOFF・NEXT・ROADMAP・QUESTIONS・DECISIONS・BACKLOG は書き換えない(本体の作業役だけが書く)。チケットのファイルに作業ログ・引き継ぎメモ・判断待ち・分けたもの。ブランチにコミット・push とマージはしない・最後に rebase main。
- 判断が要る時も止まらない: ユーザーが決めることは案ごとの影響とおすすめを書き、取り消しやすいおすすめ案を「仮(ユーザー未確認)」で進める。
  影響は、エンジンの仕組みなら**エンジンを使う人(作り手)から見た違い**で、何を聞いているのか分かる形で書く(ゲームの言葉〔魔法の強さ等〕に置き換えない)。
  ゲームの中身なら「プレイヤーと遊びへの影響」で書く(CLAUDE.md §5・D-476)。
- 返答の形式: 15 行以内(結果・ブランチの先頭・テスト・判断待ち・司令塔がマージ後に直すもの・運転メモ)。
- 技術の注意(毎回書く): 64bit の「0 で止める引き算」を HLSL に書かない / シミュに浮動小数点を書かない(`half`・`round` も弾かれる)/ ルートの SRV・UAV に GetDimensions を使わない /
  HW の Work Graph は反応の核を 1 ノードに 2 か所まで・子にインラインのセルを何個も持たせない / 内側のループを return で抜けない / ルート署名は多重解像度で 64/64 語 /
  溢れ: 頁を配ったら溢れを空にする・刻みの段を足したら RecordWideRetry・塊の表の j 番目は WideTableEntryWord / 公開リポジトリなので魔法・魔素の中身を書かない(D-006)/ `near`・`linear` は名前に使わない /
  魔法のパッチ(magic_patch)は D-493 で外した(T-0496。法則を試すのは表の書き換えと実験室で)/ 負荷で遅れることは不具合として扱う(D-468)。

## ユーザーとのやり取り
- ユーザーは返事できないことがある。判断待ちは QUESTIONS とチケットに溜め、巡目の区切りに「あとで見てほしい判断」として短く伝える。
- 巡目の区切りに 4〜6 行で結果を伝える(チケット名を遊び・機能の言葉で)。
- ユーザーが止めたら、見回りの予約を消し、状態(push していない分・壊れているテスト・止まった作業ツリー)を伝える。
- PC が重い・GPU のリセット(nvlddmkm の 153)が増えたら、並走の GPU の使い方を疑う(2026-10-11 は 24 時間に 36 回)。
