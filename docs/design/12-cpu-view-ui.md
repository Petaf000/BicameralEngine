# 12 CPU 側: 窓・入力・UI・文字(L4 詳細設計)

対応する決定: D-107・D-308(CPU は View と Controller。Model を書き換えない)/ D-115(日本語+英語)/ D-116(パッドとキーボード・マウス)/ D-416(ゲーム UI は自作)/ D-319(会話は保留)

## 目的
CPU がやること全部を 1 か所にまとめ、「CPU は世界を書き換えない」をコードの構造で守る。

## 1. CPU の仕事(これ以外はしない)
| 仕事 | 内容 |
|---|---|
| 窓とスワップチェイン | 窓の作成・サイズ変更・全画面・Present・フレームのペース(待てるスワップチェインで) |
| 入力 | キーボード・マウス・パッドを読み、**操作(アクション)**に直す。割り当ては変更できる |
| コマンドを出す | 操作・UI の選択・会話の選択・セーブ要求を、コマンド(06 §3)にしてキューへ |
| 投げる | 1 フレームの刻みの数を決め、事前に記録したコマンドリストを投げる(06 §4) |
| 読む | リングからイベントとスナップショットを読む |
| UI | タイトル・オプション・図鑑・会話の画面などを、スナップショットから作る |
| 音 | 11 |
| セーブ I/O・ストリーミングの I/O | 15・05 |
| Luau | View 側のスクリプト(UI の流れ・会話の流れ・依頼の流れ)。13 |

## 2. 構造で守る
- CPU のコードは GPU の世界のバッファへの書き込みの手段を持たない。持っているのは「コマンドキューへ書く」関数だけ。
- スナップショットは読み取り専用の構造体(型で const)。スナップショットを書き換えても世界は変わらない。

## 3. 入力
- 操作の種類(移動・カメラ・使う・切り替え…)は Luau で定義(ゲームの中身)。割り当ての初期値もそこ。
- パッドは GameInput または XInput(未確認: どちらを使うか。GameInput の対応状況を確かめる)。
- カメラの向きもコマンドにする(09 §7)。1 フレームに 1 つ、最新の向きを送る。

## 4. UI(自作。D-416)
- 自由度のため、ゲームの UI は自作する。描画は自分のレンダラーで行い、UI の中でシェーダー効果・3D(図鑑の生き物を回す)・自由なアニメーションを使える。
- 仕組み: 要素の木(レイアウト: フレックスボックス相当から始める)+ スタイル(Luau で書く)+ データの結び付け(スナップショット → 表示)+ アニメーション + 入力(パッドの空間ナビゲーション・マウス・キーボード・IME)。
- UI の見た目と画面の流れは Luau で書く(D-318)。外注の UI デザイナーが触れるよう、スタイルの書き方は文書にする。
- エディタの UI は Dear ImGui(14)。ゲームの UI とは別。

## 5. 文字
- 文字列はすべて外に出す(キー → 日本語・英語)。Luau の表か CSV。キーが無ければ開発中はキーそのものを赤で表示。
- フォントは日本語用と英語用。字形の読み込みは FreeType、文字の並べ方は自作の UI の中で行う。組版の細部(ルビ・縦書き)は要るかどうかをユーザーが決める(中身)。

## 6. 会話(D-319 で保留)
- 決まっていること: 会話の表示と分岐の進行は CPU(View)。結果(依頼を受けた・物を渡した)はコマンドとして GPU へ。NPC は GPU の世界の状態を 1〜3 フレーム遅れのスナップショットで見る。
- 会話を生成する場合も、生成された文は View の中だけにあり、世界への影響はコマンドとして記録されるので、世界の決定性は壊れない。

## テスト
- 入力の割り当て → コマンドの列が期待通り(CPU だけのテスト)。
- UI の画面ごとの画像比較(スナップショットを固定値にして)。
