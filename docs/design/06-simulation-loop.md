# 06 シミュレーションの 1 刻みとフレーム(L4 詳細設計)

対応する決定: ADR-0011(1 フレームの予算ぶんずつ投げる)/ D-107・D-308(Model は GPU、CPU はコマンドとスナップショット)/ D-201・D-202(上限なし、重いと世界が遅くなる)/ D-205(決定性)/ D-302(できる限り Work Graphs)/ D-305(固定刻み)/ ADR-0003(世代同期)

## 目的
世界の時間がどう進み、CPU と GPU が何を渡し合い、描画とどう並ぶかを決める。

## 1. 時間
- 世界の時間は**刻み**で進む。1 刻み = 世界時間 1/60 秒。刻みの番号(uint64)が世界の時計。
- 1 刻みの結果は「前の刻みの状態 + その刻みに当たるコマンド」だけで決まる。現実の時間・フレームレート・GPU の速さは結果に入らない。
- **現実の時間との比は固定しない**(D-409): 重いと遅くなり、ゲーム側も意図して変えられる(スローの演出。§6)。
- 速い現象(爆発・燃焼の急な立ち上がり)は刻みを細分する(1/2^k、k ≤ 6)。
  - 第 1 段(最初に作る): **全体で同じ細分**。活性の全ブロックの「必要な細分」の最大を GPU で求め、その刻みは全体をその回数に分ける。決定的だが、1 か所の爆発で全体が重くなる。
  - 第 2 段(研究 R-LOOP-1): ブロックごと・レベルごとの細分(局所時間刻み)。境界の流れは粗い方の刻みでまとめて受け渡して保存則を守る。**多重解像度(17 §4)では必須**。

## 2. 1 刻みの段(全部 GPU。CPU は投げるだけ)
| 段 | 内容 | 形 |
|---|---|---|
| 1 コマンド適用 | この刻みに当たるコマンドを番号順に適用(プレイヤーの入力・魔法・会話の選択・エディタの変更) | Compute |
| 2 活性の整理 | 活性ブロックの一覧を作る。境界を越えた流れで隣を起こす。静かになったブロックを粗い層へ | Work Graphs |
| 3 輸送 | 熱の伝導・気体の流れ・水の流れ(07) | 反復が決まっている → Work Graphs と Compute を測って安い方(D-302) |
| 4 反応 | 活性セルで反応表を評価(02)。音・光・物の発生をレコードとして出す | Work Graphs |
| 5 物理 | 物の接触生成(Work Graphs)→ ソルバー(08) | Work Graphs + 測って安い方 |
| 6 生き物 | 行動の選択・移動・アニメーション(09) | Work Graphs + Compute |
| 7 結合 | 物の部品と、重なるセルとの熱・物質のやり取り | Compute |
| 8 粗い層 | 60 刻みに 1 回: 成長・回復・天候・生き物の数(05 §4) | Compute |
| 9 検査と出力 | 保存則の合計(デバッグ)・状態のハッシュ・イベントとスナップショットをリングへ | Compute |

- 各段は**世代同期**: 前の世代を読み、次の世代に書く(ADR-0003)。セルは自分の新しい値を、隣の古い値から計算する(gather)。
- 面の流れは面の持ち主(マイナス側のセル)が 1 回だけ計算し、両側がその同じ値を足し引きする → 保存則が構造的に守られる。
- 1 刻みで Work Graphs の連鎖は深さ 32 まで(仕様の上限)。反応の連鎖は「刻みをまたいで」進むので、この上限に当たらない。

## 3. CPU と GPU の境界(D-308)
### CPU → GPU: コマンドキュー
```
struct Command { uint64 targetTick; uint32 sequence; uint16 type; uint16 size; uint8 payload[48]; }  // 64 バイト
```
- CPU はコマンドに「適用する刻み」を付ける(= まだ記録していない最初の適用の単位の刻み)。同じ刻みの中では sequence の順に適用する。
- 再生ファイル = 初期状態(シード + 差分 + 表の版)+ コマンドの列。これで世界が完全に再現できる(D-110 の共有の形式でもある)。

#### 実装(T-0086。`sim/command.h`・`sim/probe_sim`・`shaders/sim/probe_tick.hlsl`)
- **コマンドは GPU のキューで自分の刻みまで待つ。** 環状のバッファ(容量 1024、見出しに末尾と先頭の通し番号)。
  各フレームのリストの先頭で `EnqueueCommands` がそのフレームの新しいコマンド(最大 256)を末尾へ足し、
  適用の単位(`ApplyCommands`)が先頭から `targetTick == 今の刻み` の間を取り出して適用する。フレームにその刻みの適用の単位が無くてもよい
  (T-0012 までは CPU が「適用の単位があるフレーム」まで持っていた)。
- 足すのは CPU だけなので、末尾の番号と空き(`ProbeSim::FreeCommandSlots`)は CPU が控える。CPU の約束(`RecordFrame` が確かめる):
  足すコマンドは (targetTick, sequence) の昇順・targetTick は `NextApplyTick`(まだ記録していない最初の適用の刻み)以上・数は空き以下。
  約束を破って遅れて届いたものは GPU が捨て、`PROBE_EVENT_COMMAND_LATE` のイベントと Debug の assert で知らせる。
- 適用は **1 スレッドがキューの順に**(同じ刻みの中の順番が結果に効く本物のコマンドも決定的に適用できる)。数が増えて重くなったら、
  種類ごとに分ける(T-0005 以降。順番に依存しないもの(つつきの max など)は並列でよい)。
- 空きが足りないとき、クリックは CPU で次のフレームまで待つ(適用の刻みは遅れる)。再生は数刻み(8)先まで先に足す。

#### イベントの並べ方(T-0086)
- 刻みの中のイベントは、まず刻みの一時置き場(256 個。順不同に atomic で追記)へ。刻みの最後の単位(段 9)で `FlushEvents` が
  1 グループの bitonic sort でキー(種類 << 32 | 場所)の順に並べ、リング(フレームごとの読み戻し)へ刻みの順に写す。
  → CPU が読む並びは (刻み, 種類, 場所) の順で、フレームへの分け方にも GPU の中の順番にも依存しない(`gpu_probe_sim_test`)。
- 溢れ: 一時置き場の分とリング(1 フレーム 1024 個)の分を「落とした数」として数えて CPU へ(Warning)。溢れたときにどれが残るかは決めない
  (イベントは View に渡すだけで世界の結果に入らない)。本物の段でイベントが多くなったら、一時置き場を大きくし、並べ方を複数グループの基数ソートにする。

### GPU → CPU: 待たないリングバッファ
- イベント(音・発見・UI に知らせること): 各刻みの終わりに、キー(刻み・種類・場所)で並べてからリングに書く。
- スナップショット(UI 用: プレイヤーの状態・図鑑・近くの NPC の状態など): 数刻みに 1 回、決まった形の構造体で書く。
- CPU は 1〜3 フレーム遅れで読む。読めていない分は捨てずに次に読む(リングが一杯なら GPU 側で「落とした数」を数えて Warning)。
- デバッグ出力(printf・assert・Work Graphs のカウンタ)も同じ仕組みの別のリング(16)。

## 4. フレーム(描画とシミュの並び)
- シミュは **compute キュー**、描画は **direct キュー**で並べて走らせる。同期は GPU のフェンスだけ(CPU は待たない)。
- シミュは「描画用の抽出」(変わったブロックの面・煙のボリューム・物と生き物の姿勢)を、1 フレームに 1 回まで、そのフレームに投げた単位の後ろで刻みの境界の状態から作る。
  描画用の抽出は **3 組**で、描画は完成済みの最新を読む。抽出 n は、終わっている抽出が n − 2 以上のときだけ作る(読んでいる 1 組 + 書いている 2 組。
  T-0004 で 2 組から改め、T-0012 で「バッチ」から「フレームごとの投入」に置き換えた)。
- 描画は最新の 2 刻みの間を補間して見せる(物と生き物の姿勢)。
- 1 フレームに投げる刻みの数は CPU が決める:
  - 目標 = 現実の経過時間に相当する刻み数(60 刻み/秒)。
  - GPU の時間は、数フレーム前のタイムスタンプを待たずに読み戻して知る。追いつかないなら投げる数を減らす → **世界の時間が遅くなる**(D-202)。結果は変わらない(§1)。
  - 1 刻みが非常に重いとき(巨大な延焼)は、段の中の活性ブロックの一覧を分割して、何回かに分けて投げる(描画のキューが間に入れるように)。
  - **分けるだけでは足りない。描画より前に compute に積んでおく仕事を、1 フレームの予算以下に保つ**(R-LOOP-2 の結論。T-0085):
    - この GPU では、描画は compute のキューに先に積まれた仕事が終わるまで始まらない(同時に走らず、Dispatch や投入の切れ目でも割り込まない)。
    - だから CPU が毎フレーム「そのフレームの予算ぶんの単位」だけを compute に投げ、その後ろに描画を投げる。1 刻みは何フレームにまたがってよい
      (描画は完成済みの最新の抽出を読むので、刻みの途中でも止まらない)。
    - 単位(Dispatch か DispatchGraph のまとまり)の長さの目安は 1〜3 ms。1.25 ms まで細かくしても費用は見えなかった。予算に合わせて単位の数を決める。
    - 予算 = 目標のフレーム時間 − 描画の GPU 時間 − 余裕。**目標 fps は設定で、既定 60**(ADR-0011)。重いときは描画を目標まで落とし、残りを全部シミュへ。
    - T-0004 の「バッチを 2 つまで重ねて投げる」は、重いと描画の前に 2 バッチ分が積まれるので、T-0012 でこの規則に置き換えた(§4.1)。
- 描画の目標は 30fps 以上(D-201)。シミュが重くても描画とカメラと UI は止めない。

### 4.1 実装(T-0004・T-0012。`engine/src/frame/frame_loop.cpp`)
- 窓(`platform/window`)→ 待てるスワップチェイン(`gpu/swap_chain`。フリップ・3 枚・先行 2〜3 フレーム)の待ちがフレームの歩調。
  CPU が GPU のフェンスを待つのは、起動・終了・窓の大きさの変更のときだけ(`gpu::Queue::Flush`)。
- **1 刻み = 決まった数の単位の列**(`sim/probe_sim`: 適用 → 拡散 → 重さ × k → ハッシュ。単位の間は UAV バリア)。フレームの切れ目はどの単位の間にも来てよい。
- **1 フレームに投げる単位の数は `frame::SimScheduler`**(ADR-0011): 予算 = 1000 / 目標 fps − 描画の GPU 時間(平均)− 余裕 1 ms(下限 0.5 ms)。
  単位ごとの GPU 時間の平均(単位の間のタイムスタンプを数フレーム遅れで読む)を足して予算に入る数だけ。まだ測っていない単位は予算いっぱいと見なす。
  刻みを始めてよいのは「現実の時間 × 60 × 速さ(D-409)」の未処理が 1 以上のときだけ。未処理が 8 刻みを超えたら捨てる(世界が遅くなる。D-202)。
  刻みの途中なら、1 単位が予算より重くても 1 つは進める(世界を止めない)。
- シミュのリストは **ProbeSim のフレームの枠(4)ごとに 1 本を毎フレーム記録し直す**(同じリストは前の実行が終わるまで投げ直せない。debug layer [553])。
  記録はルート定数(刻みの番号)と Dispatch だけ(CPU のフレームの時間は T-0004 と同程度。docs/perf.md)。描画のリストは作るときに 1 度だけ記録して使い回す。
  枠の前のリストが終わっていなければ、そのフレームはシミュを投げない(見送り)。T-0004 の「刻みの数ごとに記録したリストを使い回す」形はやめた
  (刻みの数を ExecuteIndirect の数で切り替える形は、空の ExecuteIndirect が 1 回約 30 µs かかったのでその前にやめている。docs/perf.md)。
- 抽出 n は組 n % 3 に書き、compute キューは「組 n % 3 を最後に読んだ描画」のフェンスを GPU の上で待ってから走る。
  終わっている抽出が n − 2 より前なら、そのフレームは抽出しない。描画は CPU から見て終わっている最新の抽出を読む → 描画がシミュを待つことは無い。
- GPU → CPU は `gpu::ReadbackRing`(追記バッファ + 枠ごとの読み戻しのバッファ)と、ハッシュの表の読み戻し。フェンスが進んだ枠だけ読む
  (イベント・刻みごとの状態のハッシュ・単位ごとのタイムスタンプ・デバッグの出力)。
- **状態のハッシュ**(段 9): 刻み t の最後の単位が S(t + 1) の要約 Σ Mix64(セルの番号, 値)(mod 2^64)を取る。和は順番に依存しないので、
  GPU は wave の和 + 64bit の atomic で足し、CPU リファレンスは順に足して同じ値になる(`ProbeStateHash`)。
- 描画のキューは優先度 HIGH(効果は見えなかったが害も無い。R-LOOP-2)。
- 仮の世界(`sim/probe_sim`: クリックした所が熱くなって広がる)の中身は T-0005 以降で本物の段に置き換える。単位の列・予算・ハッシュ・抽出の形はそのまま使う。

### 4.2 1 フレームのシミュの予算(T-0085 の測定。docs/perf.md 2026-09-30)
1 刻み 36 ms の重さで、1 フレームにシミュへ回す時間を変えると(RTX 3070 Ti・165Hz):
| 1 フレームのシミュ | 描画 | 世界の速さ(最大に対して) |
|---|---|---|
| 分けない(今の形) | 28 fps | 100% |
| 約 30 ms | 54 fps | 96% |
| 約 13 ms | 82 fps | 97% |
| 5 ms | 165 fps(画面の上限) | 73% |
- 世界の速さの損は「フレームの切れ目で GPU が空く分」。予算が大きいほど損は減り、描画の fps は下がる。
- 予算 = 目標のフレーム時間 − 描画の GPU 時間 − 余裕。単位の数は、読み戻した単位の時間から決める(待たない。§4.1 の SimScheduler)。
- **T-0012 の実装で(予算ぶんを 1 本のリストにまとめて 1 回で投げる)**: 36 ms/刻み・目標 60 で描画 68 fps・世界は最大の 98%、
  22.5 ms/刻みで 71 fps・96%、目標 165 で 165 fps。1 単位 = 1 回の投入(T-0085)と同じく描画は戻る → 1 本のリストで足りる(docs/perf.md)。
- 未確認: GPU 側で「まだ投げていない描画のフェンス」を compute に待たせる形(CPU が歩調を取らない)は、同じリストの二重投入という誤りと一緒に試して固まったので、
  正しい形では未確認(今の形で足りているので急がない)。
- 1 単位が予算より重いと(分けない 22.5 ms の重さ)、その単位のフレームだけ描画が遅れる(平均 69 fps でも、重い単位のフレームは 22 ms)。単位は 1〜3 ms に分ける。
- Work Graphs への影響(T-0005): 1 回の DispatchGraph が長くなりすぎないよう、1 回で扱うレコードの数に上限を持たせ、続きは次の単位へ回す形にする。

## 5. 決定性のための細則(04 の規則を 1 刻みに当てはめたもの)
- 段 4 の反応で生まれる物・音・光のレコードは、Work Graphs の中では順不同に出てくる。段 9 でキー(刻み・セル ID・規則 ID・番号)で並べてから使う。
- 物の生成(燃えた木から炭の塊が落ちるなど)の ID は「親の ID + 親の中の番号」。
- 1 セルの中で複数の反応が同じ物質を取り合うときの配り方は 02 で決める(順番に依存しない比例配分)。

## 6. 重さの予告とスローの演出(D-409・D-410)
- 世界の時間の流れ(現実 1 秒あたりの刻み数)は、2 つの要因で決まる: **重さ**(追いつけない分だけ遅くなる)と、**ゲーム側の指定**(演出で意図して遅く/速くする)。遅い方が効く。
- **予告**: 影響の大きいコマンド(広範囲の魔法など。どのコマンドが対象かはゲーム側が Luau で指定)が入ったら、適用の前に GPU で軽い見積もりの段を走らせる:
  届く範囲(活性になりそうなブロック数)・反応で出るエネルギーの見積もり・過去の計測から換算した 1 刻みの時間 → 「予想の遅さ(世界時間 1 秒が現実の何秒になるか)と、続く長さ」。
  見積もりはイベントとして CPU へ(06 §3)→ ゲーム側(Luau)が演出を組む(溜めのスロー・エフェクト・カメラ・効果音)。
- **途中経過**: 実際の刻みの時間と残りの見積もりを、数フレームごとにイベントで届ける。演出は合わせて伸び縮みする。
- 見積もりは予測なので外れる(R-LOOP-3)。**結果(世界の状態)は見積もりに一切依存しない**(見積もりは View に渡すだけ)。
- ゲーム側が指定したスローも、刻みの中身は変えない(現実の時間との比だけが変わる)。

## テスト
- 刻みの数を変えずにフレームの分け方だけ変えても(1 フレーム 1 刻み / 1 フレーム 4 刻み / 刻みを分割して投げる)、状態のハッシュ列が同じ。
  → `gpu_probe_sim_test`(T-0012): 1 刻みずつ / 8 刻みずつ / 1 単位ずつ / 刻みの途中で切るばらばら / 重さの単位を足してばらばら、が CPU のハッシュ列とビット一致(GPU・WARP)。
- コマンドの列を再生して、同じハッシュ列になる。
  → `gpu_probe_sim_test`(T-0086): 途中のフレームで届くコマンドを記録 → 再生ファイルに書いて読む → 別の分け方(重さの単位を足したばらばら)で再生して
  40 刻みのハッシュが全部一致(GPU・WARP)。ctest の `window_replay_record` / `window_replay_play`: 窓(`--auto-click --record`)で記録し、
  `--replay --sim-load --sim-split --target-fps 30` で再生して全部一致(ハードウェアの GPU)。
- GPU を重くして(わざと巨大な延焼)、世界の時間が遅くなり、描画は 30fps を保つ。

## 研究(時間の打ち切りなし。D-411)
成功の基準と、うまくいかない時に試す代案の順を書く。諦めるのは原理的に無理と分かった時だけ(ユーザーと判断)。
- R-LOOP-1 局所時間刻み(多重解像度で必須): 基準は、レベルの境界で保存則がビット単位で守られ、1 か所の細かい計算が全体を重くしないこと。代案: 境界の流れを粗い刻みごとに積算して一括で受け渡す(帳尻合わせ)。
- R-LOOP-3 重さの予告の精度(§6): 見積もりと実際の時間の差を記録し、見積もりの式を直していく。
- R-LOOP-2 compute キューと direct キューの並走で、描画が 30fps を保てるか。保てなければ、シミュを投げる単位を小さくする。
  - 途中経過(2026-09-30、T-0004、RTX 3070 Ti): 描画はシミュを待たない形にしたが、1 刻みの Dispatch が長い(25 ms 以上)と、
    描画の fps がシミュのバッチの速さまで落ちる(34〜46 ms/刻みで 23 fps、描画のキューを HIGH にして 30 fps)。
    12 ms/刻みまでは描画 100 fps 以上。原因(GPU の同時実行・プリエンプション・DWM)は未確認。次に試すのは、1 刻みを分けて投げる(§4)と、
    分けた単位の長さと描画の fps の関係を測ること(T-0012)。
  - **結論(2026-09-30、T-0085、RTX 3070 Ti・HAGS 有効)**: 原因は「描画は、compute のキューに先に積まれた仕事が終わるまで始まらない」こと。
    1 本のリストの中で 16 個の Dispatch に分けても、16 回の別々の投入にしても、fps は変わらなかった(45 → 45 / 44)。vsync・描画のキューの優先度も効かない。
    CPU が 1 フレームに予算ぶんだけ投げると、22.5 ms/刻みの重さで 164 fps・世界 94%(1 フレーム 5.6 ms)。描画は 30fps を保てる → §4 の規則と §4.2。
